The iPhone Safari failure

You were right that it was tied to the Draco work — but not because Draco was implemented wrongly. It was tied to the commit that came with it: the lazy grid, which made the viewer build-and-dispose on scroll for the first time. Three latent bugs only became reachable at that point, and they compound.

  1. A viewer is disposed while its model is still downloading

    Scroll past a card faster than its .glb loads — trivially easy at 20 MB — and dispose() runs first. Neither load callback checked for that.

  2. The model arrives into a dead renderer

    The ready path then ran frameCamera() and renderer.render() against a context forceContextLoss() had already killed — the repeating THREE.WebGLRenderer: Context Lost spam. Worse, the decoded geometry was assigned after teardown had already run, so it was never freed.

  3. And every viewer was being retained anyway

    The real killer, and it predates the Draco work entirely. Each viewer pushed its cancelNudge into a module-level array that nothing removed from, and bound three pointer listeners to its wrapper <div> that nothing unbound. Both are closures over the whole viewer — renderer, scene, decoded mesh. Every viewer the grid had ever built stayed in memory for the life of the page.

  4. iOS hits its ceiling and reloads the tab

    Safari enforces a page-wide total canvas budget, not a per-canvas one, and is far tighter on memory than desktop. A linearly growing pile of retained renderers and multi-hundred-MB decoded meshes reaches it quickly — which surfaces as the page silently reloading itself, with nothing useful in the console.

Measured: 26 live WebGLRenderers, Scenes and TrackballControls retained after two scroll passes with zero viewers on screen, climbing by 26 more every two passes. After the fix: flat, at exactly what's visible.

Verified by heap snapshot with forced GC and a retainer-path walk — performance.memory is quantized by Chrome and reported the same fabricated number before and after, which is worth knowing if you ever measure this yourself.

What the Draco setup itself needed

The one thing already right was the most important: a single shared DRACOLoader. A loader per model is the most-reported cause of Draco failing specifically on iOS (three.js #22445), since each instance spawns its own worker pool and WASM heap.

  • Worker limit lowered from 4 to 2. Every viewer decodes exactly one model, so the other workers could never be busy — they were just extra copies of the WASM heap on the most memory-constrained device.
  • preload() on first model load. The decoder's ~336 KB was being fetched after the .glb arrived, a wasted serial round trip. Now it downloads alongside.
  • Decoder path resolved against document.baseURI. The bare relative string would break silently, and only for Draco models, if a page ever moved into a subdirectory.
  • A shared GLTFLoader too, instead of constructing one per load.

Loading, as it feels now

Beyond raw bytes, three things were making the homepage feel worse than its file sizes implied.

FixedLOAD-1Every model started downloading at once

Lazy building bounded how many viewers existed, but not how many started loading. A brisk scroll crossed all eight build margins in about a second, so every model downloaded simultaneously with bandwidth split eight ways — the slowest possible route to seeing any single one.

Capped at two concurrent loads, queued in scroll order. Cards that scroll back out of range before their turn are dropped from the queue rather than fetched.

js/main.js — MAX_CONCURRENT_MODEL_LOADS, pumpLoadQueue, entry.wantsViewer
FixedLOAD-2The placeholder was the wrong image, and it jumped

Cards showed icons, which auto-render.js deliberately trims and rescales to a fixed 80% of the frame so thumbnails match each other. That's exactly wrong as a stand-in for the live canvas: measured on Furcula, the icon drew the ring 1.232× larger than the model in both axes and re-centred it ~6% sideways.

Cards now use fallback-img — the same capture saved without that treatment, which is what it exists for. It matches the live canvas to 0.999× wide / 0.997× tall, centre within 0.1%. The viewer also fades in over 400 ms rather than swapping, and the old double-swap (icon → poster → model) is gone.

js/main.js — buildCard, revealViewer · js/three-viewer.js — options.poster
FixedLOAD-3Render-blocking fonts and a late-discovered data fetch

All seven pages opened with two DNS+TLS handshakes and a render-blocking third-party stylesheet for 37 KB of Geist Mono. Separately, data/series.json — which gates everything on every page, including the hero — wasn't discoverable until series.js had downloaded and run.

Geist Mono self-hosted next to DINish (2 latin subsets, 37 KB). Fonts and series.json preloaded in the head. The site now makes zero external requests, which the code comments already claimed on its behalf.

FixedPERF-1Idle viewers redrew 60× a second, forever

The animate loop ended in an unconditional render(). A model sitting perfectly still still issued a full WebGL draw every frame — on the homepage, for every live card at once, producing pixels identical to the ones already on screen. On a phone that's constant battery and thermal load, and the throttling it causes makes the next real interaction worse.

Draws only when the camera has actually moved past a sub-pixel threshold, or a resize / metal swap flags it. The rAF loop still runs; only the draw is skipped.

js/three-viewer.js — drawIfChanged, needsRender
FixedPERF-2The HDRI was decoded once per card

The comment explaining why the PMREM texture can't be shared across renderers is correct. But the pixels have no context affinity, and decoding a 2K RGBE file is tens of milliseconds of main-thread work that was being repeated for every grid card.

The decode is memoized per URL and shared; each viewer still builds its own PMREM from that one buffer, so the GPU lifecycle is unchanged. Also fixed: the PMREM render target was never disposed, only its texture.

js/three-viewer.js — loadHdrSource, loadEnvironment
FixedBUG-1Stray taps could navigate to a product

A card's click-vs-drag check measured every pointerup against startX/startY, even when no pointerdown had landed on that card. A drag begun on the page background and released over a card, or a second finger lifting during a two-finger scroll, measured against a stale 0,0 — a zero-distance "click" — and navigated.

Tracks the originating pointerId; unmatched pointerup events are ignored.

UX findings

Ranked by what actually blocks a visitor. The engineering is now in better shape than the content and the flow — none of the items below are performance problems.

BlockingUX-17 of 8 products have no price

Only Furcula has real prices. The other seven are 0 on every metal, which renders as "Price on request" — but there is no mechanism anywhere on the site to make a request. Seven of eight products are effectively un-buyable, and the grid gives no hint which is which until you open it.

Fill in per-metal-specs, or — if pricing genuinely isn't settled — make "Price on request" a working action rather than a dead end.

data/series/bones/products.json
BlockingUX-2Product pages show a table of dashes

7 of 8 have an empty description, rendering the literal string "No description yet.". All 8 have empty weight and composition, so the Characteristics table on every product is a list of em-dashes. For jewelry, material and weight aren't nice-to-haves — they're most of what a buyer is deciding on.

Populate both. Until then, hide an empty row rather than rendering a dash — an absent row reads as "not applicable", a dash reads as "unfinished".

BlockingUX-3Checkout requires accepting terms that don't exist

The checkout gate won't enable until "I have read and accept the terms & conditions" is ticked. That link goes to terms.html, which contains a heading and nothing else. The same is true of Archives and Creation process, both linked from the header menu on all seven pages — a visitor exploring the nav lands on blank pages twice.

Terms is the urgent one; it sits on the purchase path and is a legal surface. For the other two, either write them or drop them from the menu until they exist.

BlockingUX-4The size guide opens an empty panel

#sizeModalGuideContent and #modifyModalGuideContent have markup and styling but nothing ever writes into them. Tapping "Size guide" expands a blank box. This sits directly on the critical path: it's the control someone reaches for at the exact moment they don't know which of 52–62 mm to pick, and it's also the moment they're most likely to abandon.

Render real guidance — a mm-to-size conversion, and the string-and-ruler method. The category already carries sizes and unit in data/series.json, so it can be driven from data rather than hardcoded.

HighUX-5No way to reach anyone, from anywhere

There's no contact page, no email, no form, no social link on any of the seven pages. Combined with UX-1 and the checkout stub, a visitor who wants one of these rings has no action available to them at all. js/main.js still carries a #contactForm handler for a form that doesn't exist on any page.

Even a mailto: in the footer would change this from "no path" to "a path". The handler is already waiting.

HighUX-6A large part of a phone screen won't scroll

The 3D viewer sets touch-action: none so TrackballControls can rotate freely. On a grid card the viewer is clamp(210px, 45vw, 795px) square — on a phone, a substantial block of the screen where a vertical swipe does nothing. The carousel already solved this properly, with pan-y plus an axis lock that hands vertical gestures back to the browser.

Apply the carousel's axis-lock approach to the grid viewer: keep horizontal drags for rotation, let vertical ones scroll the page.

HighUX-7Nothing respects reduced motion

Zero occurrences of prefers-reduced-motion across the CSS, the scripts and the hero bundle. The site animates a lot: a 200 vh scroll-pinned x-ray wipe, the idle model nudge, the ease-back-to-pose reset, the selection-bar slide-in, the carousel. For a vestibular-sensitive visitor the homepage hero in particular is the hardest kind of motion to tolerate, and it's unavoidable — it's the entry.

Honour the media query: skip the idle nudge and the pose reset, shorten transitions, and let the hero settle to its end state rather than animating through it.

HighUX-8Every page is titled "em·ji·ve", and 6 of 7 have no h1

Only product.html sets a real title, and it does so at runtime — so search results, browser history and shared links all show the same six characters for Archives, Terms, the order page and the homepage alike. Only the product page has an <h1>; the homepage has no heading structure at all.

Static, distinct <title> per page, and a real h1 on each — visually hidden on the homepage if the design doesn't want one.

HighUX-9Muted text fails AA contrast

--category-col: #777777 on --bg: #f8f8f8 is 4.22:1, under the 4.5:1 needed for normal text. It isn't decorative — it carries the category label under every product name, the spec labels, and the loading and empty states. On white it's 4.48:1, still marginally short.

Deliberately not done

Two things I stopped short of, both because they're your call rather than mine.

Your callOPEN-1Triangle counts are still very high

Draco fixes download size, not GPU cost. rib-cage-extended is 2.32 M triangles, rib-cage 1.25 M, suture 721 K — for rings rendered into a ~400 px box. Those three also have vertex-to-triangle ratios near 1.9:1, meaning they're essentially unwelded (faceted exports with no shared edges), which is why automatic simplification barely touches them: --simplify=0.25 cuts the other five cleanly (cartilage 762 K → 190 K) but moves these three less than 8%.

Re-export from Blender with smooth shading and merge-by-distance. That's a modelling change that alters the silhouette, and these same files are what auto-render.js regenerates every icon and top shot from — so it isn't something to run unasked. npm run optimize-models -- --simplify=0.25 is there when you want it.

Two new npm scripts, and how to use them
  • npm run optimize-models — strips unused textures/UVs, welds, Draco-compresses every product .glb, then re-reads each written file and decodes it back to confirm the triangle count and bounding box survived. Exits non-zero if any model fails that round trip. Run it after adding any model. --dry-run reports without writing.
  • npm run optimize-images — converts stray PNG/JPEG under assets/ to WebP and prints the path renames for you to apply in products.json. It deliberately doesn't edit the catalog itself.
  • Neither runs during build. They rewrite binaries in place, so they're deliberate passes you review — git is the undo.

Suggested order

If the goal is making the site sellable, the engineering is no longer what's in the way.

  • Prices, descriptions, weight and composition (UX-1, UX-2) — nothing else changes the outcome while seven of eight products can't be bought and every spec table is blank.
  • Write terms, and fill the size guide (UX-3, UX-4) — both sit directly on the purchase path, and both are small.
  • Give people a way to respond (UX-5, UX-14) — an email capture on the order page and a contact route in the footer.
  • The accessibility set (UX-7, UX-8, UX-9, UX-10, UX-11) — reduced motion, titles and headings, contrast, focus handling, pressed state. Together they're maybe a day.
  • Mobile scroll trapping (UX-6) — the carousel already contains the solution to copy.
  • Re-export the three dense models (OPEN-1) — the last real performance item, and the only one that needs Blender rather than code.
