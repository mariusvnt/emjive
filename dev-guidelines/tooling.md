# Tooling

## `package.json` scripts

```json
"dev": "vite", "build": "vite build", "preview": "vite preview", "auto-render": "node scripts/auto-render.js"
```

`dev`/`build`/`preview` are genuinely wired up and work; `npm run dev` is the documented way to run the site locally (see `procedures.md`) and is required specifically for `js/three-viewer.js`'s bare-specifier imports (`three`, `three/addons/...`) — this is a real, live-site file (loaded as `<script type="module">`), not a dev-only one, so Vite is a hard requirement to run the site at all now, not an optional convenience. `three` is a real runtime `dependencies` entry (not just a devDependency) since `three-viewer.js` imports it directly; `puppeteer-core`/`sharp` are `devDependencies`, used only by `auto-render.js`.

## `vite.config.js`

Exists specifically because `npm run build`'s output needs to be *deployable*, not just correct in dev — a plain `vite build` with no config silently produces a broken `dist/` for this site (confirmed by inspecting the output directly): Vite only treats `index.html` as a build entry by default (every other page would ship unprocessed, with the same unresolved bare-specifier `three` import that breaks on any plain static host), and it can't bundle or copy classic `<script src>` tags at all (so `js/main.js`, `js/product.js`, and the other classic scripts vanish from the build entirely — not just left unbundled, actually absent) or trace paths that only exist as runtime string data (a series' `products.json` icon/model paths, the hero-bundle paths in `data/series.json`, the HDRI path in `three-viewer.js`). Two things fix this: `build.rollupOptions.input` lists all seven HTML pages explicitly, and a small inline `closeBundle` plugin copies `js/`, `assets/`, `data/`, and `series/` into `dist/` verbatim after the real build runs. `series/` is on that list for the same reason as `data/` — it holds each series' hero bundle, referenced only as string paths and injected at runtime, which is also why a hero bundle's JS can never use a bare specifier. Also sets `base: "/emjive/"` — GitHub Pages project-page-specific, see below and `README.md`'s "Deploying" section for why and when to change it.

## `.github/workflows/deploy.yml`

Builds and publishes to GitHub Pages on every push to `main` (standard `actions/upload-pages-artifact` + `actions/deploy-pages` pattern). This is explicitly a stopgap for the current `mariusvnt.github.io/emjive/` URL, not the site's intended long-term host — see `README.md`'s "Deploying" section for the full picture, including exactly what to change/delete when the site moves to its own domain.

## `scripts/auto-render.js` (~720 lines)

Renders per-metal product icons, "top shot" images, and metal-sample swatches via a real (GPU-accelerated) headless Chrome instance, driving the site's **own** `js/three-viewer.js` / `window.EmjiveModelViewer` rather than a hand-duplicated reimplementation — so a render can't silently drift from what the live site actually shows. See `procedures.md` for the invocation/usage walkthrough; this doc covers the internal architecture instead.

**Major pieces:**

- `findChrome()` — checks `CHROME_PATH` env var first, then a hardcoded list of common install paths per OS; throws if none found.
- `startServer()` — a bare `http.createServer` serving repo files by path, plus a special `/__render__.html` route serving an in-memory `HARNESS_HTML` string. Has a path-traversal guard (resolves the requested path and checks it still starts with the repo root before serving).
- `HARNESS_HTML` — a minimal page with an `<script type="importmap">` resolving `three`/`three/addons/*` straight from `/node_modules/...` (this bare server has no bundler of its own to do that resolution, unlike the real site's Vite build) and a `<script type="module" src="js/three-viewer.js">`. Its own inline module script defines three page-side render functions on top of that: `window.__renderTarget(product, metalKey, sizePx)` (icons, calling `window.EmjiveModelViewer(product, metalKey, {transparentBackground: true, static: true, onReady})` directly — `static` skips the idle-nudge hint and continuous animate loop so nothing can shift the framing before the screenshot), `window.__renderTopShot(...)` (same — `scene.environment` is already the studio HDRI by the time `onReady` fires, no override needed, unlike an earlier version that swapped in a cached `RoomEnvironment` PMREM texture instead — but additionally adds a procedural soft-shadow plane, adds an invisible finger occluder, and calls `handle.setCameraOrbit({ rotation: 0, tilt: 0, zoom })` to force a straight-down view — the direct replacement for the old model-viewer-based harness's `jumpCameraToGoal()`+`camera-orbit`-attribute combo), and `window.__renderSwatch(metalKey, sizePx)` (calls `window.EmjiveModelViewer.buildMaterialSwatch(metalKey, sizePx, {onReady})` — a plain cylinder, not any product, see `client-scripts.md`/`procedures.md`). All three wait two `requestAnimationFrame`s after their own completion signal before setting `window.__renderReady = true`, so the *settled* frame gets captured, not a stale one. A `disposeCurrentHandle()` helper runs before every render call — it disposes the previous `WebGLRenderer` (a fresh one is built per render, since a full run creates many contexts in one browser session and undisposed ones eventually exhaust the browser's WebGL context limit) — `js/three-viewer.js`'s own HDRI loading needs no equivalent help, since it's loaded fresh per instance rather than cached across contexts (see `client-scripts.md`). `window.EmjiveModelViewer`/`buildMaterialSwatch` can both return `null` if WebGL context creation fails (see `client-scripts.md`) — unlike the live site, which falls back to a static icon image in that case, this tool has no equivalent fallback (rendering the icon *is* the job), so all three functions instead throw a descriptive `Error` naming the product/metal (or just the metal, for swatches) that failed, aborting the run rather than crashing on a confusing null dereference or silently shipping an incomplete set of renders.
- `addFingerOccluder(scene, box)` (top-shot only) — a real finger is never present in these renders, so a straight-down shot of a ring would otherwise show whatever geometry actually sits under its visible top surface: the band's own inner wall, or (Furcula's split shank specifically) a sightline straight through a gap to the far side. This fakes the occlusion a finger would provide with an invisible plane — `MeshBasicMaterial({colorWrite: false, depthWrite: true})`, so it blocks whatever's behind it in the depth test without ever contributing a visible pixel — positioned at the model's own vertical midpoint (`box.min.y + size.y * 0.5`) and given `renderOrder: -1` so it draws (and claims the depth buffer) before the model regardless of THREE's own distance-sorted opaque order. A uniform 50%-height cut across every product was settled on only after several fancier per-product approaches (a radius-fitted cylinder to leave untouched geometry provably safe, then per-angle radii to hug an elongated shank more tightly, then deriving the cutoff straight from the nearest real surface via raycasting) each failed a different way against the three products current at the time — see the function's own comment in the source for the specifics. Deliberate trade-off, not a bug: this fully fixes Furcula's shank but does visibly cut into Disc's own lower band surface, since Disc's decorative material happens to start lower relative to its own bounding box than the other two.
- Because that occluder writes depth but not color, it can't share a render pass with the existing soft-shadow plane without a visible side effect: tried directly, the occluder winning the depth test against the shadow (drawn later, in the transparent pass) erased the shadow's own color exactly where it did, punching a hole in the gradient at the "finger" location. Fixed with a two-pass render instead — the model hidden on its own `THREE.Layers` layer for a first pass so the shadow draws alone against a genuinely empty canvas, then the model and the occluder brought back for a second, non-clearing pass with the shadow specifically re-hidden (redrawing it a second time double-blended the area the occluder wasn't covering, a subtler version of the same artifact). The shadow plane's own size (`sphere.radius` multiplier) was also tightened, separately — the previous multiplier left faint non-zero alpha reaching the captured frame's own edge, invisible at this render's native 1024×1024 but a visible translucent rectangle once composited small onto the hero's hand (see below).
- `captureTarget`/`captureTopShotTarget`/`captureSwatchTarget` → `renderIcon`/`renderTopShot`/`renderSwatch` — drive Puppeteer to call the harness functions, screenshot the result, and encode to WebP via `sharp` (`quality: 92`). Captures happen at 2x the final pixel size then downscale — real GPU MSAA already handles edge antialiasing; this step is purely for retina-sharp source pixels. `renderSwatch` needs no cropping (unlike an earlier version that rendered an actual product close-up) — the cylinder `buildMaterialSwatch` builds is already framed to fill the whole square.
- `updateProductMetalFieldInText(text, product, blockKey, metal, newRelPath)` — the regex-based JSON text patcher. Doesn't re-parse/re-stringify the whole file (see `data.md` — that would flatten its hand-aligned formatting). Instead: finds the product's block via its unique `"id": "<id>"` anchor, slices to the next `"id":` occurrence (or EOF), then within that slice matches `"<blockKey>":\s*\{[^}]*\}` (works for both the top-level `icons` object and the nested `assets.top-shot` object, since the regex only needs to be unique *within* one product's slice — this is also exactly why it can't be used to match `assets` itself, which also contains the plain-string `xray` field and would break the "no nested braces" assumption). Returns `null` rather than throwing if either regex fails to match, so the caller can warn and skip instead of corrupting the file.
- `productFolder(seriesSlug, product)` — builds a product's render output folder (`assets/series/<slug>/products/<slug(name)>_<category>/`) **from the series layout**, rather than inferring it from `path.dirname(product.model)` as it used to. That inference couldn't tell one series' tree from another's, and wrote to the repo root for any product without a model yet, since `path.dirname("")` is `"."`. The trade-off is that `assets.md`'s `<slug>_<category>` folder convention is now load-bearing: a hand-renamed folder gets a *new* one rather than being silently found. A warning fires when `product.model` sits outside the predicted folder, which doubles as a check that no model was missed by a move.
- `warnCategoryDrift(seriesIndex, targets)` — warns on the two category invariants nothing else enforces: a series declaring a category outside `series.json`'s global vocabulary, and a product whose category its own series doesn't declare (it renders in the unfiltered grid but no filter button can reach it). This is the only thing that has the index and every series' products parsed at once. An empty `sizes` list is *not* an error — it deliberately disables the Select button (see `data.md`).
- `main()` — parses metal args (validated against `series.json`'s top-level `metals`) and an optional `--series=<slug>` to narrow the run, finds Chrome, starts the server, launches Puppeteer with GPU-forcing flags (`--use-angle=d3d11` added only on `win32`; `--enable-gpu-rasterization --ignore-gpu-blocklist` on all platforms), then **checks the actual WebGL renderer string** via `WEBGL_debug_renderer_info` and warns if it contains "swiftshader"/"software" (meaning no real GPU/MSAA was used — see `CHROME_PATH` in `procedures.md`). For each metal, for each series, for each product: renders+writes the icon (patching `icons`, deleting the old file if the path changed), renders+writes the top shot (same for `assets.top-shot`); after all products for that metal, renders the one metal-sample swatch (global, not per-series). Writes each series' patched text back only if it actually changed. Runs in a `try/finally` that closes the browser and HTTP server either way.

  **One target per series file, with its `raw`/`text`/`data` kept strictly bundled together.** Product ids are only unique *within* a file now, so a shared top-level `productsText` could have one file's text patched using another file's product and still satisfy `updateProductMetalFieldInText`'s `"id"` anchor.
