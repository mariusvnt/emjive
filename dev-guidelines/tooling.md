# Tooling

## `package.json` scripts

```json
"dev": "vite", "build": "vite build", "preview": "vite preview",
"auto-render": "node scripts/auto-render.js", "scene-tool": "node scripts/scene-tool-server.js",
"json-tool": "node scripts/json-tool-server.js"
```

`dev`/`build`/`preview` are genuinely wired up and work; `npm run dev` is the documented way to run the site locally (see `procedures.md`) and is required specifically for `js/three-viewer.js`'s bare-specifier imports (`three`, `three/addons/...`) — this is a real, live-site file (loaded as `<script type="module">`), not a dev-only one, so Vite is a hard requirement to run the site at all now, not an optional convenience. `three` is a real runtime `dependencies` entry (not just a devDependency) since `three-viewer.js` imports it directly; `puppeteer-core`/`sharp` are `devDependencies`, used only by `auto-render.js`. `scene-tool` and `json-tool` each start their own, completely separate bare Node server (see below for both) — neither touches Vite at all, and both can run alongside `npm run dev` (and each other) on their own ports.

## `vite.config.js`

Exists specifically because `npm run build`'s output needs to be *deployable*, not just correct in dev — a plain `vite build` with no config silently produces a broken `dist/` for this site (confirmed by inspecting the output directly): Vite only treats `index.html` as a build entry by default (every other page would ship unprocessed, with the same unresolved bare-specifier `three` import that breaks on any plain static host), and it can't bundle or copy classic `<script src>` tags at all (so `js/main.js`, `js/product.js`, and the other classic scripts vanish from the build entirely — not just left unbundled, actually absent) or trace paths that only exist as runtime string data (a series' `products.json` icon/model paths, the hero-bundle paths in `data/series.json`, the HDRI path in `three-viewer.js`). Two things fix this: `build.rollupOptions.input` lists all seven HTML pages explicitly, and a small inline `closeBundle` plugin copies `js/`, `assets/`, `data/`, and `series/` into `dist/` verbatim after the real build runs. `series/` is on that list for the same reason as `data/` — it holds each series' hero bundle, referenced only as string paths and injected at runtime, which is also why a hero bundle's JS can never use a bare specifier. Also sets `base: "/emjive/"` — GitHub Pages project-page-specific, see below and `README.md`'s "Deploying" section for why and when to change it.

## `.github/workflows/deploy.yml`

Builds and publishes to GitHub Pages on every push to `main` (standard `actions/upload-pages-artifact` + `actions/deploy-pages` pattern). This is explicitly a stopgap for the current `mariusvnt.github.io/emjive/` URL, not the site's intended long-term host — see `README.md`'s "Deploying" section for the full picture, including exactly what to change/delete when the site moves to its own domain.

## `scripts/auto-render.js` (~720 lines)

Renders per-metal product icons, "top shot" images, and metal-sample swatches via a real (GPU-accelerated) headless Chrome instance, driving the site's **own** `js/three-viewer.js` / `window.EmjiveModelViewer` rather than a hand-duplicated reimplementation — so a render can't silently drift from what the live site actually shows. See `procedures.md` for the invocation/usage walkthrough; this doc covers the internal architecture instead.

**Major pieces:**

- `findChrome()` — checks `CHROME_PATH` env var first, then a hardcoded list of common install paths per OS; throws if none found.
- `startServer()` — a bare `http.createServer` serving repo files by path, plus a special `/__render__.html` route serving an in-memory `HARNESS_HTML` string. Has a path-traversal guard (resolves the requested path and checks it still starts with the repo root before serving).
- `HARNESS_HTML` — a minimal page with an `<script type="importmap">` resolving `three`/`three/addons/*` straight from `/node_modules/...` (this bare server has no bundler of its own to do that resolution, unlike the real site's Vite build) and a `<script type="module" src="js/three-viewer.js">`. Its own inline module script defines three page-side render functions on top of that: `window.__renderTarget(product, metalKey, sizePx, hdriRelPath)` (the icon/fallback-img capture, calling `window.EmjiveModelViewer(product, metalKey, {transparentBackground: true, static: true, hdri: hdriRelPath, onReady})` directly — `static` skips the idle-nudge hint and continuous animate loop so nothing can shift the framing before the screenshot; the Node side then saves this one screenshot two ways, see `renderIconAndFallback` below), `window.__renderTopShot(...)` (same, plus `hdriRelPath` — `scene.environment` is already whichever HDRI this series resolved to by the time `onReady` fires, no override needed, unlike an earlier version that swapped in a cached `RoomEnvironment` PMREM texture instead — but additionally adds a procedural soft-shadow plane, adds an invisible finger occluder, and calls `handle.setCameraOrbit({ rotation: 0, tilt: 0, zoom })` to force a straight-down view — the direct replacement for the old model-viewer-based harness's `jumpCameraToGoal()`+`camera-orbit`-attribute combo), and `window.__renderSwatch(metalKey, sizePx, primitive, hdriRelPath, cameraConfig)` (builds a minimal stub `{ name, "3d-viewer-camera-default": cameraConfig }` and calls `window.EmjiveModelViewer(stubProduct, metalKey, {transparentBackground: true, static: true, primitive, hdri: hdriRelPath, onReady})` — `options.primitive` is what used to be a separate `buildMaterialSwatch()` function, retired once swatches needed the same draggable/savable camera orbit products already had; see `client-scripts.md`). All three wait two `requestAnimationFrame`s after their own completion signal before setting `window.__renderReady = true`, so the *settled* frame gets captured, not a stale one. A `disposeCurrentHandle()` helper runs before every render call — it disposes the previous `WebGLRenderer` (a fresh one is built per render, since a full run creates many contexts in one browser session and undisposed ones eventually exhaust the browser's WebGL context limit) — `js/three-viewer.js`'s own HDRI loading needs no equivalent help, since it's loaded fresh per instance rather than cached across contexts (see `client-scripts.md`). `window.EmjiveModelViewer` can return `null` if WebGL context creation fails (see `client-scripts.md`) — unlike the live site, which falls back to a static icon image in that case, this tool has no equivalent fallback (rendering the icon *is* the job), so all three functions instead throw a descriptive `Error` naming the product/metal (or just the metal, for swatches) that failed, aborting the run rather than crashing on a confusing null dereference or silently shipping an incomplete set of renders.
- `addFingerOccluder(scene, box)` (top-shot only) — a real finger is never present in these renders, so a straight-down shot of a ring would otherwise show whatever geometry actually sits under its visible top surface: the band's own inner wall, or (Furcula's split shank specifically) a sightline straight through a gap to the far side. This fakes the occlusion a finger would provide with an invisible plane — `MeshBasicMaterial({colorWrite: false, depthWrite: true})`, so it blocks whatever's behind it in the depth test without ever contributing a visible pixel — positioned at the model's own vertical midpoint (`box.min.y + size.y * 0.5`) and given `renderOrder: -1` so it draws (and claims the depth buffer) before the model regardless of THREE's own distance-sorted opaque order. A uniform 50%-height cut across every product was settled on only after several fancier per-product approaches (a radius-fitted cylinder to leave untouched geometry provably safe, then per-angle radii to hug an elongated shank more tightly, then deriving the cutoff straight from the nearest real surface via raycasting) each failed a different way against the three products current at the time — see the function's own comment in the source for the specifics. Deliberate trade-off, not a bug: this fully fixes Furcula's shank but does visibly cut into Disc's own lower band surface, since Disc's decorative material happens to start lower relative to its own bounding box than the other two.
- Because that occluder writes depth but not color, it can't share a render pass with the existing soft-shadow plane without a visible side effect: tried directly, the occluder winning the depth test against the shadow (drawn later, in the transparent pass) erased the shadow's own color exactly where it did, punching a hole in the gradient at the "finger" location. Fixed with a two-pass render instead — the model hidden on its own `THREE.Layers` layer for a first pass so the shadow draws alone against a genuinely empty canvas, then the model and the occluder brought back for a second, non-clearing pass with the shadow specifically re-hidden (redrawing it a second time double-blended the area the occluder wasn't covering, a subtler version of the same artifact). The shadow plane's own size (`sphere.radius` multiplier) was also tightened, separately — the previous multiplier left faint non-zero alpha reaching the captured frame's own edge, invisible at this render's native 1024×1024 but a visible translucent rectangle once composited small onto the hero's hand (see below).
- `captureTarget`/`captureTopShotTarget`/`captureSwatchTarget` → `renderIconAndFallback`/`renderTopShot`/`renderSwatch` — drive Puppeteer to call the harness functions, screenshot the result, and encode to WebP via `sharp` (`quality: 92`). Captures happen at 2x the final pixel size then downscale — real GPU MSAA already handles edge antialiasing; this step is purely for retina-sharp source pixels. `renderIconAndFallback` calls `captureTarget` **once** per product/metal and saves that one screenshot buffer two ways, in this order: first as-is (a plain resize, `FALLBACK_IMG_SIZE` = `ICON_SIZE`) for `fallback-img`, then through `normalizeIconFraming` (trim/re-center/pad) for `icon` — see `data.md` for why the two need different treatment. `renderSwatch`/`captureSwatchTarget` also take `primitive`/`hdriRelPath`/`cameraConfig` now (`data/series.json`'s `swatch-primitive`/`swatch-hdri`/`swatch-camera`, resolved in `main()` below) — no cropping needed either way, but full-frame coverage is no longer a *guarantee* the way the retired `buildMaterialSwatch()`'s bespoke cylinder-only formula gave: a cylinder or box (rectangular silhouette) still fills the frame exactly, a sphere or torus (circular/curved silhouette) geometrically can't without leaving corner gaps — see `client-scripts.md`'s `options.primitive`.
- `updateProductMetalFieldInText(text, product, blockKey, metal, newRelPath)` — the regex-based JSON text patcher. Doesn't re-parse/re-stringify the whole file (see `data.md` — that would flatten its hand-aligned formatting). Instead: finds the product's block via its unique `"id": "<id>"` anchor, slices to the next `"id":` occurrence (or EOF), then within that slice matches `"<blockKey>":\s*\{[^}]*\}` (works for the nested `assets.icons`, `assets.fallback-img`, and `assets.top-shot` objects alike, since the regex only needs to be unique *within* one product's slice — this is also exactly why it can't be used to match `assets` itself, which also contains plain-string/array fields like `model`/`xray`/`photos` and would break the "no nested braces" assumption). Returns `null` rather than throwing if either regex fails to match, so the caller can warn and skip instead of corrupting the file. `scripts/scene-tool-server.js` (below) reuses this exact `"id"`-anchor/non-nested-braces idiom for its own patchers, adapted for whole-block numeric/string replacements instead of a per-metal string swap.
- `productFolder(seriesSlug, product)` — builds a product's render output folder (`assets/series/<slug>/products/<slug(name)>_<category>/`) **from the series layout**, rather than inferring it from `path.dirname(product.assets.model)` as it used to. That inference couldn't tell one series' tree from another's, and wrote to the repo root for any product without a model yet, since `path.dirname("")` is `"."`. The trade-off is that `assets.md`'s `<slug>_<category>` folder convention is now load-bearing: a hand-renamed folder gets a *new* one rather than being silently found. A warning fires when `product.assets.model` sits outside the predicted folder, which doubles as a check that no model was missed by a move.
- `warnCategoryDrift(seriesIndex, targets)` — warns on the two category invariants nothing else enforces: a series declaring a category outside `series.json`'s global vocabulary, and a product whose category its own series doesn't declare (it renders in the unfiltered grid but no filter button can reach it). This is the only thing that has the index and every series' products parsed at once. An empty `sizes` list is *not* an error — it deliberately disables the Select button (see `data.md`). Two siblings, same "warn but don't crash on data-integrity drift" shape, checking every series regardless of `--series`: `warnHdriDrift(seriesIndex)` (a series' `hdri` key not in the top-level `hdris` map) and `warnSwatchSceneDrift(seriesIndex)` (`swatch-hdri` not in `hdris`, or `swatch-primitive` not one of `buildPrimitiveMesh()`'s known shapes).
- `main()` — parses metal args (validated against `series.json`'s top-level `metals`) and an optional `--series=<slug>` to narrow the run, finds Chrome, starts the server, launches Puppeteer with GPU-forcing flags (`--use-angle=d3d11` added only on `win32`; `--enable-gpu-rasterization --ignore-gpu-blocklist` on all platforms), then **checks the actual WebGL renderer string** via `WEBGL_debug_renderer_info` and warns if it contains "swiftshader"/"software" (meaning no real GPU/MSAA was used — see `CHROME_PATH` in `procedures.md`). Also resolves each series' own `hdri` (into `target.hdri`, threaded through every render call for that series) and the three top-level `swatch-*` fields once, with the same fallbacks `js/three-viewer.js`'s own defaults use if any are absent. For each metal, for each series, for each product: renders+writes the fallback-img and icon in one pass (patching `assets.fallback-img` and `assets.icons`, deleting each old file if its path changed), renders+writes the top shot (same for `assets.top-shot`); after all products for that metal, renders the one metal-sample swatch (global, not per-series, using the resolved `swatch-*` config). Writes each series' patched text back only if it actually changed. Runs in a `try/finally` that closes the browser and HTTP server either way.

  **One target per series file, with its `raw`/`text`/`data` kept strictly bundled together.** Product ids are only unique *within* a file now, so a shared top-level `productsText` could have one file's text patched using another file's product and still satisfy `updateProductMetalFieldInText`'s `"id"` anchor.

## `scripts/scene-tool-server.js` + `scene-tool.html`

A standalone dev page (`npm run scene-tool`, then open `scene-tool.html`) for tuning a product's camera angle, a series'/the swatch renderer's HDRI, the swatch-scene primitive+camera, and a metal's shader — all as a live preview through the site's real `window.EmjiveModelViewer`, with a Save action that text-patches the relevant source file in place. Written to replace the old "drag it, hand-edit the JSON, reload, compare, repeat" workflow `procedures.md` used to document for `3d-viewer-camera-default` — see that doc's "Setting a model's default view" for the actual usage walkthrough; this section covers the server's own architecture.

Deliberately built as a **second, completely separate** bare `http` server (port 5200) rather than a Vite dev-middleware route or a browser File System Access API — it mirrors `scripts/auto-render.js`'s own already-proven pattern (bare server + import-map-resolved `three-viewer.js`) instead of tangling a dev-only save endpoint into `vite.config.js` (whose whole reason for existing is production-build correctness), and needs no Chromium-only permission dance the way FSA would. Never added to `vite.config.js`'s `build.rollupOptions.input`, so it's naturally absent from `npm run build`'s output — same as `auto-render.js` itself.

- **Static serving** — same `MIME` map and path-traversal guard as `auto-render.js`'s own `startServer()` (duplicated rather than imported/shared — a little redundancy here is consistent with this repo's own tolerance for that trade-off, e.g. `vite.config.js`'s `copyFilesVitesBuildCantTrace()` comment), including `/node_modules/...` so `scene-tool.html`'s own import map (same `three`/`three/addons/*` resolution `HARNESS_HTML` uses) can be served.
- **Five save endpoints**, one per {concern × mode}, so `scene-tool.html`'s tick boxes only fire the ones actually ticked: `/api/save-product-camera` (product mode, patches that product's `3d-viewer-camera-default`), `/api/save-series-hdri` (product mode, patches that product's series' `hdri`), `/api/save-swatch-camera` (primitive mode, patches `swatch-primitive` + `swatch-camera` together — the primitive choice rides along with the camera save, mirroring how a product's own identity is implicit whenever its camera is saved), `/api/save-swatch-hdri` (primitive mode, patches `swatch-hdri`), `/api/save-metal-shader` (either mode, patches `METAL_PRESETS` in `js/three-viewer.js` itself — the one save target that isn't JSON). Every endpoint re-reads its target file fresh per request (this server is long-lived across many separate Save clicks, unlike `auto-render.js`'s one-shot batch read), validates before touching disk, and writes only on a successful patch match — otherwise a 4xx with a clear "field not found, add it by hand first" message rather than inserting a new key.
- **Patchers** — `updateCameraDefaultInText`/`updateSeriesHdriInText`/`updateSwatchSceneInText`/`updateMetalPresetInText`, all variations on `auto-render.js`'s own `"id"`-anchor, non-nested-braces block-scoping idiom (see `updateProductMetalFieldInText` above), adapted for whole-block numeric/string replacements instead of a per-metal string-value swap. `updateMetalPresetInText` is the one that patches JS source rather than JSON — bounded to `METAL_PRESETS`'s own object-literal span (`"var METAL_PRESETS = {"` to the first `"};"` after it) before matching the one metal's sub-block within it, so it can never touch anything else in the 800-line file.
- **`scene-tool.html`** itself — a single self-contained file (inline `<style>`/`<script type="module">`), not split into a separate JS file, mirroring how `auto-render.js`'s own `HARNESS_HTML` is one big inline string. One cascading selection (HDRI → Model [a flat list, `<optgroup>`-separated into every series' products and the four built-in primitives] → Metal) drives a single shared viewer built via `window.EmjiveModelViewer(product, metal, {freeOrbit: true, hdri, primitive})` — see `client-scripts.md` for what `freeOrbit`/`primitive`/`target`/`dispose()` actually do. Camera rotation/tilt/zoom are both draggable (release and it stays exactly there) and directly typeable (three number inputs, each skipped by the read-back loop while it has focus so live dragging can't fight your typing). Metal-shader sliders mutate `window.EmjiveModelViewer.METAL_PRESETS[metal]` in place and re-invoke `applyMetal()` for an instant, no-rebuild preview.

## `scripts/json-tool-server.js` + `json-tool.html`

A standalone dev page (`npm run json-tool`, port 5201, then open `json-tool.html`) for editing `data/series.json`'s global parameters (`featured`/`categories`/`hdris`/`metals`) and editing, adding, or removing a series or a product — including drag-and-drop for the hand-owned asset files (3D model, x-ray, extra photos). Written to replace the old "hand-edit `products.json`, get the folder-naming convention or the per-metal-map shape wrong, `auto-render` warns about it after the fact" workflow `procedures.md` used to be the only guide for — see that doc's "Adding a product"/"Adding a category"/"Adding a series" sections for the actual usage walkthrough; this section covers the tool's own architecture.

Three scope decisions worth knowing before reading the source, all enforced structurally rather than just by convention:

1. **No `auto-render` integration** — never shells out to it or touches Puppeteer/`sharp`. It only writes JSON + hand-owned asset files; regenerating icons stays a manual `npm run auto-render` afterward (see "Re-rendering icons and metal swatches" in `procedures.md`).
2. **Never writes `assets.icons`/`assets.fallback-img`/`assets.top-shot`, for any metal.** The UI has no upload slot for them at all (a plain reminder paragraph stands in their place instead), and the shared block-renderer (below) always copies those three per-metal maps verbatim from the current on-disk product rather than from form input — there's no code path here that could touch them even by accident.
3. **A new metal only ever touches the top-level `metals` array.** `js/three-viewer.js`'s `METAL_PRESETS` and `css/style.css`'s swatch rule are never opened by this tool — adding/removing a metal here shows an on-screen reminder about those two still-manual edits (see "Choosing a product's metal" in `procedures.md`), same three-places list that section has always described.

Deliberately a **third, completely separate** bare `http` server, same reasoning as `scene-tool-server.js`'s own header comment (mirrors `auto-render.js`'s proven bare-server pattern rather than tangling a dev-only save endpoint into `vite.config.js`). Never added to `vite.config.js`'s `build.rollupOptions.input`, so it's naturally absent from `npm run build`'s output, same as the other two tools. Unlike `scene-tool.html`, it has **no 3D preview at all** — no `three` import map, nothing like `scene-tool.html`'s live viewer — camera angle/HDRI/metal-shader/swatch-scene tuning all stay `scene-tool.html`'s job; this page's camera/HDRI fields are plain typed inputs with a footer pointer to `npm run scene-tool`.

- **`scripts/json-tool-blocks.js`** — a plain sibling module, pure functions only (no `fs`/`http`), so its output can be sanity-checked by eyeballing it against real file text without touching disk. Two families of helper:
  - `insertBeforeArrayClose`/`insertBeforeObjectClose`/`appendToInlineStringArray` (add) and `removeArrayEntryInText`/`removeObjectEntryInText`/`removeFromInlineStringArray` (remove) — genuinely new primitives beyond what `scene-tool-server.js`/`auto-render.js` ever needed, since those two only ever patch a field that already exists; this tool also has to grow or shrink a JSON collection (`products[]`, `series[]`, `categories{}`, `hdris{}`, `metals[]`). Bracket-depth counting (`findMatchingClose`) is string-aware, so a literal `]`/`}`/`"` inside a quoted value can never be mistaken for real structure. `removeObjectEntryInText` reconstructs the surviving entries from scratch (canonical spacing) rather than patching around the removed one's own comma in place; `removeArrayEntryInText` deletes exactly one adjacent comma (trailing if present, else leading) so the array stays valid regardless of whether the removed entry was first, middle, or last.
  - `renderProductBlock`/`renderSeriesBlock` — full-block renderers used for BOTH adding and editing a product (and for adding a series), so the two code paths can't drift into producing different formatting. Field order/shape mirrors the real hand-authored files exactly (see `data.md`). `findBlockSpanByAnchor` locates a whole `{ ... }` block by a unique `"id"`/`"slug"` field inside it (walking back to the block's real opening `{` and forward to its real matching `}`, unlike `auto-render.js`'s/`scene-tool-server.js`'s own anchored patchers, which only ever need a span wide enough to regex a small field within) — what makes both full-block replacement (edit) and clean removal possible.
  - This repo's hand-aligned JSON columns aren't byte-for-byte consistent to begin with (confirmed directly — e.g. one product's `per-metal-specs` row has alignment spaces its sibling rows don't, another product's `top-shot` block is collapsed to one line where every other product's is multi-line), so this module targets clean, consistent, canonical spacing rather than chasing an exact reproduction of the source's own inconsistencies — accepted trade-off: saving any single field re-normalizes that *one product's* block spacing (never the rest of the file).
- **Destructive actions** (remove category/hdri/metal/series/product) sit behind the browser's native `confirm()` on the client, and a blocking check server-side wherever something else in the catalog still depends on it — a category/hdri still declared/used by a series or product, a metal still some product's `default-metal`, a series that's currently `featured`, either metals or series refusing to drop to zero. Removing a metal cascades: every product in every series gets its block re-rendered against the new (shorter) metals list, which — since `renderProductBlock` only ever emits keys for the metals it's given — is sufficient to strip that metal's key from `per-metal-specs`/`icons`/`fallback-img`/`top-shot` everywhere, with no separate per-object key-deletion step needed. Removing a series or a product deletes its real folders too (`assets/series/<slug>/`, `series/<slug>/`, `data/series/<slug>/` for a series; the one product folder under `assets/series/<slug>/products/` for a product) via `fs.rmSync(..., {recursive: true})`, guarded by a regex check on the computed folder path before any recursive delete — the same defense-in-depth `isAllowedAssetDestPath` already gives single-file writes, since a hand-corrupted `products.json`'s `name`/`category` could otherwise slugify into something path-traversal-shaped.
- **Replace/Remove pairs, immediate (not deferred to a Save button)** — shown only next to a file that's *already saved* (an existing model/xray/photo/HDRI), as opposed to the plain dropzones (used only when that slot is still empty, staged as pending until the next Save). Model/xray/photo Replace always writes to the *canonical* `<slug(name)>_{gltf,xray,photoN}.<ext>` path (deleting whatever was there before if it differs — e.g. a hand-exported `Foramen_gltf.glb`'s irregular capitalization doesn't survive a Replace, it becomes `foramen_gltf.glb`); a photo's Replace additionally keeps its array position (so it isn't just "remove + append," which would reorder the carousel). HDRI Replace is the one exception — since an HDRI isn't named from a product/category, it just overwrites the exact existing `hdris[key]` path verbatim, no rename involved.
- **File dispatch** reuses `auto-render.js`'s own `productFolder()`/`slug()` logic (from the product's *current* name+category, not wherever `assets.model` already points), so a dropped model/x-ray/photo lands at the same `assets/series/<slug>/products/<slug(name)>_<category>/` convention `assets.md` documents, under the same `<slug>_gltf.<ext>`/`<slug>_xray.<ext>`/`<Name>_photo<N>.<ext>` filenames a human would have hand-picked. Renaming a product (name or category) moves its existing model/xray/photos to the new folder (never the `icons`/`fallback-img`/`top-shot` `auto-render` owns — those are left behind, with a reminder to re-run `auto-render` there) and is blocked outright if that would collide with a different product's own folder.
