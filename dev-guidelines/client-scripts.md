# Client-side scripts

`js/` has 8 files, plus per-series hero bundles under `series/<slug>/`. 7 are plain classic scripts (`<script>` tags, no bundler needed to ship them). The 8th, `js/three-viewer.js`, is an ES module (`<script type="module">`, loaded from `<head>`) — it needs to `import` the `three` npm package, which only a module script can do. Despite the different script *kind*, it's fully part of the live site, not a dev-only file — see `tooling.md` for why an ES module is safe to mix into an otherwise-classic-script codebase, and `pages.md` for the exact load-order mechanics.

## Load order (see `pages.md` for the full page × script matrix and the `defer`/blocking explanation)

`js/series.js` is blocking in `<head>` on every page, so `window.EmjiveSeries` and `window.EmjiveHero` exist before anything else runs — including `launch-order.html`'s plain synchronous `main.js`. `selection.js` always loads before anything that touches `window.EmjiveSelection`. `three-viewer.js` (a module, in `<head>`) always finishes before `main.js`/`product.js` (both `defer`), the only two classic scripts that touch `window.EmjiveModelViewer`.

A series' `hero.js` loads later still — injected at runtime by `series.js` — which is why it's written to be inert until called.

## `js/three-viewer.js` (~750 lines) — the 3D viewer

The single shared construction path for every 3D product view on the site (homepage grid cards, the product-detail carousel) and for `scripts/auto-render.js`'s render pipeline — see `tooling.md`. A raw three.js scene per instance, driven by the `TrackballControls` addon (free, pole-crossing rotation — unlike the polar-angle-limited orbit a `<model-viewer>`-based approach would have), with a substantial amount of hand-tuned polish layered on top. Exports (all module-internal except the one exposed global):

- `METAL_PRESETS` — PBR values (`baseColorFactor`/`metallicFactor`/`roughnessFactor`) per metal name, the single source of truth repo-wide (also reused by `scripts/auto-render.js`'s harness, since it loads this exact module). Must stay in sync with `products.json`'s top-level `metals` list — see `procedures.md`'s "adding a metal" checklist. `metalToStandardMaterialParams()` converts a preset to `THREE.MeshStandardMaterial` params.
- `parseOrbitConfig()` / `parseTargetString()` — parse `product["camera-setup"]`'s `{ rotation, tilt, zoom }` object (descriptive names for what used to be a single `"<theta>deg <phi>deg <radius%>"` string, the convention a `<model-viewer camera-orbit>` attribute would have used) / `cameraTarget`'s `"Xm Ym Zm"` string format into the radians/percent the camera-framing math needs.
- `loadEnvironment(renderer)` — loads + PMREM-converts the studio HDRI into an environment map. Rebuilt fresh for every `buildThreeViewer()`/`buildMaterialSwatch()` call, never cached/shared across instances: a PMREM texture is a GPU resource tied to the specific `WebGLRenderer`/context that built it, and each instance has its own renderer. An earlier version cached this at module scope, meant to be reused across the homepage grid's several simultaneous viewers — that handed later instances a texture handle from a different (invalid) context, which silently rendered them solid black, since this scene has zero `THREE.Light` objects and depends entirely on `scene.environment` for lighting. Loading it per-instance costs a redundant fetch+decode+PMREM-generate per grid card, but normal HTTP caching keeps the repeat fetches cheap. The `HDRLoader` call has a real error callback (logs + rejects) — without one, a failed HDRI request used to leave the returned promise neither resolved nor rejected, silently hanging `Promise.all([modelPromise, environmentPromise])` below forever with zero console output.
- `buildThreeViewer(product, metalKey, options)` — builds one viewer instance: `WebGLRenderer` + `Scene` + `PerspectiveCamera` + `TrackballControls`, a `ResizeObserver`-driven canvas that always exactly fills its container, a poster `<img>` shown until the model's first frame renders, and — layered on top of the base rotation — release inertia (frame-rate-independent, re-derived from a continuous decay rate rather than assumed-60fps, with an added progressive-braking boost at low speed so a coast stops crisply instead of trailing off), a continuous two-attractor up-vector leveling drift (fades to zero at the poles, flips sign continuously through the equator rather than snapping), a bezier/slerp-based "ease back to the default pose" idle reset, and a 3-phase idle "nudge" hint (a small camera wiggle synchronized with a floating hand-icon overlay, `assets/hand-pointer-thumb-opened.svg`) — suppressed session-wide via `sessionStorage["emjive_model_interacted"]` once any instance has actually been dragged (a real drag, not just a tap — same 6px-distance-threshold pattern `main.js`'s click-navigation uses). Returns `{ el, applyMetal(newKey), setCameraOrbit(orbitConfig) }` — `setCameraOrbit` is an instant (non-animated) reposition, used only by the render harness (see `tooling.md`). Returns `null` instead, without throwing, if the browser can't grant a WebGL context (a finite per-page budget — several simultaneous viewers, bfcache-retained contexts from earlier navigations, a weak/mobile GPU) — both `main.js` and `product.js` fall back to the plain `icons[metal]` image in that case, same as a product with no `model` field at all. Calls `controls.handleResize()` on every real resize (not just once at construction) — `TrackballControls` caches the element's screen rect itself rather than measuring fresh per pointer event, and at construction time the wrapper is still a detached `<div>` (the caller hasn't appended it to the page yet), so skipping this left `screen.width` permanently stuck at 0 and every drag silently a no-op (NaN rotation deltas, falsy, quietly skipped).
- `options.static` — harness-only (never set by the interactive site): skips the idle-nudge hint and the continuous per-frame animation loop entirely (only explicit `render()` calls, so nothing can shift the framing between the harness's `onReady` firing and its screenshot being taken a few ms later). `options.transparentBackground` — also harness-only, controls `preserveDrawingBuffer` (needed for an external screenshot readback of the canvas; the interactive site never reads its own canvas back). The renderer's alpha itself is unconditional now (both the interactive site and the harness render on a genuinely transparent canvas) — an earlier version kept the interactive site's canvas opaque on purpose to dodge a subtler ACES-tone-mapping edge-blending artifact, which traded it for a much more visible bug (a solid near-black square behind every model wherever the canvas wasn't covered by geometry).
- `buildMaterialSwatch(metalKey, sizePx, options)` — harness-only, used solely by `scripts/auto-render.js` for the metal-sample swatch bars (see `procedures.md`). Builds a plain cylinder (not any actual product) with the same `METAL_PRESETS` material + shared-HDRI-loading path, framed close enough that its curved surface fills the entire square frame with no cropping needed — see the function's own comment for why a product's own geometry (a torus viewed edge-on) can't do this at any zoom. Returns `{ el, renderer, scene, camera }`, or `null` on the same WebGL-context-creation failure `buildThreeViewer()` guards against (see above) — `options.onReady` fires after the environment lands and the first frame renders.

**Exposes**: `window.EmjiveModelViewer = buildThreeViewer` — consumed by `main.js`'s grid and `product.js`'s carousel. Also `window.EmjiveModelViewer.buildMaterialSwatch` — a harness-only second export, see above.

## `js/series.js` (~320 lines) — series resolution

Loaded blocking in `<head>` on every page (see above). Fetches `data/series.json` once and exposes `window.EmjiveSeries`:

- `ready` — a promise resolving to `{ index, slug, series }`. **Everything else on the site hangs off this**; `main.js`, `product.js` and `series-page.js` all start from it rather than fetching any JSON path themselves.
- `slug`/`series` — the ACTIVE series: `?series=` if it names a real one, else `index.featured`.
- `metals` — the global metal list. `categories()` — the active series' own category subset. `categoryInfo(id)` — that category's `{ sizes, unit }` from the global vocabulary.
- `loadProducts(slug)` / `loadManifest(slug)` — **memoized per slug**, so the grid and the hero handoff share one request.
- `mainHref` / `manifestHref` / `productHref` — URL builders. They deliberately **omit `?series=` for the featured series**, so everyday URLs stay clean and links bookmarked before the refactor keep resolving.
- `requestedSlug()` — the raw `?series=` with no fallback applied. Only `series.html` uses it, so it can show a not-found state instead of silently rendering the featured series' manifest.

It also owns **hero bundle loading** on `index.html` (guarded on `#seriesHero` existing): inject the preload hints, inject the hero stylesheet, fetch the fragment and inject the hero script — all in flight at once — then clone each `<template data-series-slot>` into its slot, call `EmjiveSeriesHero.init()`, and hand the series' products to `onProducts()`. On failure it strips `body.has-series-hero` so the selection bar isn't stranded off-screen. See `pages.md` for the full contract and the anti-flash reasoning.

`window.EmjiveHero` lives here too — a plain function registry (`onScroll`/`publishScroll`), not a `CustomEvent`, because it fires once per animation frame during scroll and a registry costs no allocation per publish.

`window.EmjiveMenus` also lives here — click-away coordination for the header menu (`main.js`) and the selection-bar drawer (`selection-bar.js`), two panels that don't know about each other and can be open at once. Each registers `{ root, close() }` via `opened(panel)`/`closed(panel)` when its own open state changes; `root` spans both the panel's trigger and its content, so clicking the trigger itself is never mistaken for "away". A single `document` click listener here closes only the most-recently-opened panel when a click lands outside every currently-open one's `root` — a second outside click is needed to close the other if both happened to be open together.

## `series/<slug>/hero.js` — one per series

The hero's behavior, loaded at runtime. Assigns `window.EmjiveSeriesHero = { init(root, ctx), onProducts(products) }` and does nothing else at execution time. For Bones that means the frontier-band lift, the scroll-driven x-ray wipe, and `updateHeroRings()` — one `.reveal__ring` `<img>` per product with `onHand.visible: true` (see `data.md`), each positioned/sized/rotated via inline custom properties set from that product's own `onHand` object, so multiple rings on screen don't fight over one shared set. It gets the **full, unfiltered** product list: the rings are hero art, not a listing.

Two rules any hero bundle has to keep: no side effects at execution time (the loader parallelizes on that assumption), and no bare specifiers (Vite never sees this file, so `import "three"` would ship unresolved — call `window.EmjiveModelViewer` instead).

## `js/main.js` (~365 lines)

Loads on **every** page. Owns:

- The header hamburger menu toggle. A delegated click handler on `.site-header__row` also toggles it from anywhere in the row's empty space — same as the `+`/`-` icon — while ignoring clicks on the brand logo (which navigates home instead) or on `.menu-toggle` itself (which already has its own listener, and would double-toggle otherwise). Registers a panel with `window.EmjiveMenus` (`js/series.js`) so a click away from the whole header closes it too — see that file's doc above.
- The **category filter row**. The buttons are rendered from `EmjiveSeries.categories()` — the active series' own subset — so the row renders identically on pages that load no product data at all. It's hidden outright (`hidden` on `#siteHeaderFilter`) when that subset has one category or fewer, since there's nothing to toggle. The menu-close handler is **delegated** to the menu container, because those buttons are created after the script runs; a per-link listener would never reach them.
- **Filtering** (`applyFilter`/`toggleCategory`/`setCategories`), on the grid page only. Multi-select toggles that hide already-built cards, sync `?cat=` via `history.replaceState`, and leave the menu open so successive toggles are usable. Elsewhere the same buttons are ordinary links that navigate to the grid with one category applied. Unknown `?cat=` values are dropped against the active series' categories, so a typo shows everything rather than nothing.
- `wireModelClickNavigation(el, href)` — the 6px drag-distance-threshold click-vs-drag disambiguation, attached to a viewer's wrapper so rotating a model doesn't accidentally navigate.
- The grid rendering (`buildCard`/`renderProducts`) — one card per product from `EmjiveSeries.loadProducts()`, calling `window.EmjiveModelViewer(product, product.metal)` for any product with a `model` set. Cards are built **once** and kept in a module-scope array; see the WebGL note in `pages.md` for why filtering must never rebuild them.
- A guarded contact-form stub (`getElementById("contactForm")`) — a no-op, since no page has that element. Kept for whenever a contact form gets built (see `procedures.md`).

Owns **no hero logic at all** any more, and no `METAL_PRESETS` or viewer-construction logic — those live in the active series' hero bundle and `js/three-viewer.js` respectively. `main.js` is purely a consumer of both.

## `js/selection.js` (104 lines)

The cart/selection data layer — a thin `localStorage` wrapper. `STORAGE_KEY = "emjive_selection"`. Read/write helpers fall back to `[]` on any error (e.g. corrupted JSON). Every mutating call dispatches `new CustomEvent("emjive:selection-changed")` on `window` — the sole mechanism other scripts use to react live to a change without a page reload.

Four mutators, all index-based (an item's position in the stored array, not an id): `addItem(item)` (pushes to the end), `removeItem(index)` (splices it out), `insertItem(index, item)` (splices it back in at a specific position — `launch-order.html`'s "Undo" after Unselect, so a restored item lands back where it was rather than at the end the way `addItem` would), and `updateItem(index, patch)` (`Object.assign`s `patch` onto the existing item in place — `launch-order.html`'s "Modify," changing metal/size and the price that comes with them without moving the item to the end the way remove+add would).

**Exposes**: `window.EmjiveSelection = { getSelection, addItem, removeItem, insertItem, updateItem, clear, formatPrice }`.

**Item shape**: `{ series, productId, name, category, metal, size, price, image }` — a deliberately self-contained snapshot, so `launch-order.html` never has to re-fetch or join against any products file to render itself. `series` is what makes `productId` meaningful, since ids are only unique within one series. Selections saved before that field existed simply lack it; nothing here reads it, and `selection-bar.js`'s `itemKey()` tolerates it being absent so an existing cart doesn't read as all-new.

## `js/product.js` (728 lines) — the largest file

Owns `product.html` end to end. Resolves `?id=` via `findProduct()` — the active series first, then a scan of the remaining series in index order (each memoized), which is what keeps bare `?id=` bookmarks working now that ids are only unique per series. Then renders (by the file's own numbered section comments):

1. **Label** — name, category, per-metal thumbnail, price.
2. **Carousel** — builds slides (a 3D viewer via `window.EmjiveModelViewer` if `product.model` is set, else a fallback icon image, then any `product.photos`). No rim/arrow click zones: navigation is either a free horizontal drag (rubber-band overshoot past either end; release lands exactly where the drag left it, clamped back into bounds — no momentum coast) or a tap directly on a slide, which centers it (`centerOnSlide()`) however far from center it started. On a narrow/phone-width viewport (`isMobileCarousel()` — reuses `css/style.css`'s one existing `max-width: 640px` breakpoint, the `.product-grid` one) a real drag instead always pages exactly one slide forward/backward and centers it, committing only past a real drag distance (15% of a tile) or a fast-enough short flick (gated by a minimum distance too, so touch-event jitter on a barely-moved drag can't read as a flick) — short/slow drags spring back to the slide they started on. A pointer's horizontal-vs-vertical intent is axis-locked in `onPointerMove` (the first movement past a small slop decides it, once) so a vertical scroll starting on the strip is handed off untouched to the browser's own `touch-action: pan-y` instead of the carousel eating part of the gesture; `pointercancel` (the browser interrupting a pointer itself — that same scroll handoff is the common case) is handled separately from a clean `pointerup` specifically so an interrupted gesture is never misread as a tap. Every way a slide gets centered shares one symmetric ease-in-out transition (`CENTER_TRANSITION`; `CANCEL_TRANSITION` is the same curve, shorter, used only when a mobile drag springs back without actually changing slides). Bounds stay "first/last tile centered" (not edge-flush). Carousel geometry can only be measured once `#productDetailContent` is actually visible (`[hidden]` elements measure zero) — bounds are explicitly re-synced right after the content is unhidden.
3. **Metal picker** — re-tints the live 3D model in place via `state.modelHandle.applyMetal(metal)` (no reload, no camera reset), and separately updates the label thumbnail/fallback icon/specs/price, since only the 3D model re-tints itself automatically.
4. **Characteristics** — metal-dependent weight/composition/price from `product.metalDetails[selectedMetal]`.
5. **Select button + size modal** — sizes/units looked up by *category* (not per-product) via `EmjiveSeries.categoryInfo()`. Because that vocabulary is global rather than per-series, a cross-series hit needs no re-hydration. Standard-size buttons + a decimal-only custom input; on confirm, calls `window.EmjiveSelection.addItem({...})` with the self-contained snapshot (including the resolved series) and closes the modal.

All page state lives in one `state` object (product, metals, selected metal/size, carousel scroll offset, the live model handle, etc.).

**Notable gotchas** (from the file's own comments): `img.draggable = false` + `dragstart` prevention stops the browser's native image-drag gesture from fighting the custom pointer-drag scroll; a `pointercancel` doesn't reliably carry the pointer's final coordinates, so settling a drag interrupted mid-gesture falls back to the strip's own live position instead of the event's `clientX`; a drag that starts on the 3D model slide is left alone entirely (no `pointerdown` tracking at all) so it rotates the model via `TrackballControls` instead of paging the carousel.

## `js/selection-bar.js` (~340 lines)

The floating bar shown on `index.html` and `product.html` only (not `launch-order.html` — that page isn't in its script list at all, plus it self-guards with `if (!window.EmjiveSelection) return;`). Builds its whole DOM programmatically and appends to `<body>`.

Shows either "No selected item" or a thumbnail strip + "Order ›" link; clicking the bar (not the Order link) opens a drawer with per-item "Unselect" rows. The drawer's `max-height` is set to a real measured pixel value in JS (not a CSS trick) — this is the piece `styling.md`'s drawer note points back to — specifically so it can animate smoothly both on open/close *and* on shrinking while already open (removing a row). `setDrawerOpen(isOpen)` is the one place that changes the drawer's open state — it also registers a panel with `window.EmjiveMenus` so a click away from the bar closes the drawer, same mechanism the header menu uses (see `js/series.js` above).

This file has no notion of **which page it's on**, which was always the point. It does now subscribe to `window.EmjiveHero.onScroll` for the homepage's scroll-driven entrance — but unconditionally: the active series' hero owns all the geometry and publishes how far past its trigger the page has scrolled, and this file measures its own `.selection-bar__summary` height to turn that into a transform. On a page with no hero nothing ever publishes, so nothing ever happens and the bar just stays visible — still zero special-casing. The starting-hidden state is `css/style.css`'s `body.has-series-hero` scoping (see `pages.md` for why that stopped being `:has()`).

Listens for `window.addEventListener("emjive:selection-changed", render)` — this is how it stays live-in-sync with additions from `product.js` or removals from its own drawer.

## `js/selection-page.js` (~730 lines) — `launch-order.html`'s checkout review

Grew enormously from a simple "list + total" renderer into the whole order page's logic: item rows with a Modify/Unselect overlay, a sequential undo stack, a shipping pick, a terms toggle, and the checkout bar's gating — see `pages.md`'s `launch-order.html` section for what all of this actually looks like. Re-renders synchronously right after its own mutations (remove/insert/update) rather than listening for `emjive:selection-changed` — it's the only page without a concurrently-visible selection bar, so nothing else can change the selection while it's open.

- **Item row overlay** — `openRowOverlay(li)`/`closeOpenRow()`, one open at a time (opening a new one closes whichever was already open). Mouse hover, a tap, or keyboard focus (`focusin`/`focusout`, chosen over `focus`/`blur` specifically because they bubble, so one delegated listener on the row covers both buttons inside it) all open the same overlay; a click landing elsewhere on an already-open row — anywhere but the Modify/Unselect buttons themselves — closes it back to the normal view instead of being ignored. `suppressHoverUntilMove` guards a real browser gotcha: removing a row (or the undo bar) reflows whatever's below it up the page, and if the cursor is just sitting still, whichever row's box slides underneath it fires a genuine, unrequested `pointerenter` — this flag makes any such "phantom" enter a no-op until an actual `pointermove` confirms the cursor moved on its own.
- **Removal** — `removeRowSmoothly(li, item, index)` mirrors `selection-bar.js`'s own `handleUnselect`: the row visibly collapses first (`.order-item`'s `is-removing` class — `max-height`/padding/opacity, see `styling.md`), only mutating storage and rebuilding the list once that's actually finished (`transitionend` on `max-height`, with a 400ms fallback for reduced-motion environments that skip transitions outright). The row's own `.order-item__thumb` is pulled off before the row is discarded and carried into the undo stack, so a later restore reuses that exact, already-decoded `<img>` instead of loading a fresh one.
- **Undo** — `undoStack`, not a single pending item: every removal pushes, so unselecting several items in a row keeps all of them undo-able. The bar (`showUndoBar()`/`buildUndoBar()`) is built on `.order-item` itself for its collapse animation, and reused in place — not rebuilt — across consecutive removals/undos so it never flickers out and back in: `render()`'s own `innerHTML = ""` detaches it as a side effect of every rebuild, but that doesn't invalidate the element, just orphans it until it's `insertBefore`'d again. Clicking it pops the most recent entry (LIFO — each entry's own `index` was captured relative to the array right after *its own* removal, which is exactly what popping in that same reverse order needs to stay correct, no re-shifting math required) and restores it via `render(restore.index, restore.thumbEl)`. After the very last pending undo, the bar doesn't vanish on the spot — `lingerThenHideUndoBar()` keeps it up for `UNDO_LINGER_MS` so the restored row is actually visible first. `dismissUndo()` (a plain `setTimeout`, `UNDO_TIMEOUT_MS`, reset by every new removal or successful undo) is the only path that clears the whole stack outright.
- **Enter animation** — `playRowEnterAnimation(row)`, the mirror image of the removal collapse, used both for a row Undo restores and (a simpler inline version in `showUndoBar()`) the undo bar's own appearance. A **double** `requestAnimationFrame` — not the single one `selection-bar.js`'s own `playEnterAnimation` uses — because a single one can still land in the same frame as the `offsetWidth`-forced layout just before it, before the browser has actually painted the collapsed starting state, coalescing the whole thing into one paint with no transition ever registering. `.order-item__content`'s opacity is separately held at 0 via an inline-style override (cleared after its own `transitionend`, same set-then-clear pattern) until well after the box's own `max-height` has finished growing — fading it in any earlier would get it clipped unevenly by `.order-item`'s `overflow: hidden` while the box is still short, with different children (a fixed-height thumbnail vs. shorter text) revealing at different rates, which read as staggered rather than one row appearing as a unit.
- **Modify** — `openModifyModal(item, index)` resolves `item.series` (falling back to `EmjiveSeries.slug` for a pre-refactor selection saved without one) and re-fetches that product via `EmjiveSeries.loadProducts()`, since the stored selection snapshot doesn't carry `metalDetails`/`icons`. The popup (`#modifyModal`) reuses `product.html`'s own `.size-modal`/`.product-metals` markup and CSS wholesale rather than a page-specific clone — a metal picker plus the standard/custom size picker, pre-filled to the item's current choice, wired almost identically to `product.js`'s `wireSelectButton()`, except the static controls (input/guide toggle/backdrop/confirm/Escape) are wired exactly once and read a mutable `modifyState` object rather than closing over one fixed product, since a different row's item can sit behind this same modal on each open. Confirms via `window.EmjiveSelection.updateItem()`, recomputing price from the newly-selected metal's `metalDetails`.
- **Shipping/terms/checkout** — `SHIPPING_OPTIONS`, a small in-file placeholder array (easy to extend later, not a restructure), rendered as a single-select dot-indicator list. The terms row's click is delegated across the whole element (the dedicated tick-box or the surrounding sentence both toggle; a click on the actual `<a>` to `terms.html` navigates instead — same "toggle vs. its own separately-clickable label" split `selection-bar.js`'s drawer toggle/empty-label pair uses). `updateCheckoutGate()` disables `#orderCheckoutButton` until both a shipping option is selected and terms are ticked. The button itself is a stub — no Stripe session exists yet, so a click (once enabled) just `alert()`s that it isn't connected, the same convention `main.js`'s guarded `#contactForm` handler uses.

## Cross-cutting contracts (the highest-value section if you're changing behavior that spans files)

- **`window.EmjiveSeries`** — set by `js/series.js` (blocking, in `<head>`), consumed by `main.js`, `product.js` and `series-page.js`. The one place "which series is this, and where's its data" lives.
- **`window.EmjiveHero`** — set by `js/series.js`, published to by the active series' `hero.js`, subscribed to by `selection-bar.js`. A plain function registry, one number: how far past the hero's trigger point the page has scrolled.
- **`window.EmjiveMenus`** — set by `js/series.js`, registered with by `main.js` (header menu), `selection-bar.js` (drawer), and `selection-page.js` (each item row's Modify/Unselect overlay, one at a time). Click-away coordination: a click outside every currently-open panel's root closes only the most-recently-opened one.
- **`window.EmjiveSeriesHero`** — set by a series' `hero.js`, called by `js/series.js`. `{ init(root, ctx), onProducts(products) }`.
- **`window.EmjiveModelViewer`** — set by `three-viewer.js`, consumed by `main.js` (grid) and `product.js` (carousel). The one place 3D viewer construction/materials/camera behavior lives.
- **`window.EmjiveSelection`** — set by `selection.js`, consumed by `product.js` (add), `selection-bar.js` (add/remove/read), `selection-page.js` (remove/insert/update/read).
- **`"emjive:selection-changed"`** — `CustomEvent` on `window`, dispatched by every `selection.js` mutation. Only `selection-bar.js` listens for it.
- **`localStorage["emjive_selection"]`** — the persisted selection array (via `selection.js`).
- **`sessionStorage["emjive_model_interacted"]`** — unrelated to selection; remembers within a browsing session whether the visitor has already discovered models are draggable, to stop nudging them with the wiggle hint (set/read in `three-viewer.js`).
- **Item shape**: `{ series, productId, name, category, metal, size, price, image }` (see `selection.js` above).

## `js/series-page.js` (~55 lines)

`series.html` only. Resolves the slug via `EmjiveSeries.requestedSlug()` — deliberately **not** the fallback-applying `.slug` — loads that series' manifest, fills in the title/year/subtitle, and otherwise shows a not-found state. Rendering `manifest.json`'s `sections[]` belongs here later; the page is an empty shell by design.
