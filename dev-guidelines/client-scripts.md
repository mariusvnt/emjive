# Client-side scripts

`js/` has 8 files, plus per-series hero bundles under `series/<slug>/`. 7 are plain classic scripts (`<script>` tags, no bundler needed to ship them). The 8th, `js/three-viewer.js`, is an ES module (`<script type="module">`, loaded from `<head>`) — it needs to `import` the `three` npm package, which only a module script can do. Despite the different script *kind*, it's fully part of the live site, not a dev-only file — see `tooling.md` for why an ES module is safe to mix into an otherwise-classic-script codebase, and `pages.md` for the exact load-order mechanics.

## Load order (see `pages.md` for the full page × script matrix and the `defer`/blocking explanation)

`js/series.js` is blocking in `<head>` on every page, so `window.EmjiveSeries` and `window.EmjiveHero` exist before anything else runs — including `launch-order.html`'s plain synchronous `main.js`. `selection.js` always loads before anything that touches `window.EmjiveSelection`. `three-viewer.js` (a module, in `<head>`) always finishes before `main.js`/`product.js` (both `defer`), the only two classic scripts that touch `window.EmjiveModelViewer`.

A series' `hero.js` loads later still — injected at runtime by `series.js` — which is why it's written to be inert until called.

## `js/three-viewer.js` (~800 lines) — the 3D viewer

The single shared construction path for every 3D product view on the site (homepage grid cards, the product-detail carousel) and for `scripts/auto-render.js`'s render pipeline — see `tooling.md`. A raw three.js scene per instance, driven by the `TrackballControls` addon (free, pole-crossing rotation — unlike the polar-angle-limited orbit a `<model-viewer>`-based approach would have), with a substantial amount of hand-tuned polish layered on top. Exports (all module-internal except the one exposed global):

- **One** module-scope `DRACOLoader` and **one** module-scope `GLTFLoader`, built once at module scope with the decoder attached once — not a fresh `GLTFLoader` per load. Unlike `loadEnvironment()`'s PMREM texture, neither holds per-context state, so one of each safely serves every viewer on the page. This is not a tidiness preference: a `DRACOLoader` per load is the single most-reported cause of Draco failing specifically on **iOS Safari** (three.js#22445, discourse#68835), because each instance spawns its own worker pool and its own WASM heap. Three further settings, all aimed at the same device:
  - `setDecoderPath(new URL("assets/draco/", document.baseURI).href)` — resolved **once, absolutely**, rather than left as the bare relative string `"assets/draco/"`. `DRACOLoader` resolves its paths against the *document*, which is fine while every page sits at the repo root and breaks silently — and only for Draco models — the moment one doesn't.
  - `setWorkerLimit(...)` — lowered from the default 4 to at most 2 (`hardwareConcurrency - 1`, capped). Every viewer here decodes exactly one model and the grid keeps only a handful alive, so extra workers can never be usefully busy; each one is just another structured-clone copy of the decoder config, `wasmBinary` included.
  - `preloadDracoDecoder()` — calls `dracoLoader.preload()` the first time any model load starts, so the decoder's ~336KB downloads *in parallel with* the `.glb` rather than serially after it. Guarded so pages that never show a model never pay for it.

  Three's own decoder files are self-hosted under `assets/draco/` rather than pulled from the Google CDN three.js's examples default to, so the site stays fully offline/no-external-requests — see `assets.md`. **Every** product `.glb` now ships `KHR_draco_mesh_compression`. Without a `DRACOLoader` attached, `GLTFLoader` doesn't degrade gracefully for a Draco model — it throws synchronously (`"THREE.GLTFLoader: No DRACOLoader instance provided."`), the load promise rejects, and the viewer's own fallback behavior makes that read as an inert, undraggable model with no visible error — exactly what happened the one time rib-cage/rib-cage-extended shipped ahead of this being wired up.
- `METAL_PRESETS` — PBR values (`baseColorFactor`/`metallicFactor`/`roughnessFactor`) per metal name, the single source of truth repo-wide (also reused by `scripts/auto-render.js`'s harness, since it loads this exact module). Must stay in sync with `data/series.json`'s top-level `metals` list — see `procedures.md`'s "adding a metal" checklist. `metalToStandardMaterialParams()` converts a preset to `THREE.MeshStandardMaterial` params. Also exposed live as `window.EmjiveModelViewer.METAL_PRESETS` (tool-only — `main.js`/`product.js` never read it) — `applyMetal()` and every viewer build already re-read `METAL_PRESETS[metalKey]` fresh on every call, so `scene-tool.html`'s shader-tuning sliders just mutate this object in place and re-invoke `applyMetal()`/rebuild to preview a change instantly, with no separate override-parameter path needed.
- `parseOrbitConfig()` / `parseTargetString()` — parse `product["3d-viewer-camera-default"]`'s `{ rotation, tilt, zoom }` object (descriptive names for what used to be a single `"<theta>deg <phi>deg <radius%>"` string, the convention a `<model-viewer camera-orbit>` attribute would have used) / `cameraTarget`'s `"Xm Ym Zm"` string format into the radians/percent the camera-framing math needs.
- `loadEnvironment(renderer, hdriSrc)` — loads + PMREM-converts an HDRI into an environment map. `hdriSrc` is the caller-resolved path (`data/series.json`'s top-level `hdris` map, looked up via a series' own `hdri` key by `js/series.js`'s `hdriPath()`, or `scripts/auto-render.js`'s own equivalent resolution — see `data.md`); an omitted/unresolved value falls back to the module's own `DEFAULT_HDRI_SRC` (still `studio_kontrast_04_2k.hdr`) — this module is deliberately series-unaware, and `auto-render.js`'s headless harness never loads `js/series.js` at all, so it can't resolve a key here either way. Rebuilt fresh for every `buildThreeViewer()` call, never cached/shared across instances despite two viewers often resolving to the same file (any two showing series that picked the same `hdris` key): a PMREM texture is a GPU resource tied to the specific `WebGLRenderer`/context that built it, and each instance has its own renderer. An earlier version cached this at module scope, meant to be reused across the homepage grid's several simultaneous viewers — that handed later instances a texture handle from a different (invalid) context, which silently rendered them solid black, since this scene has zero `THREE.Light` objects and depends entirely on `scene.environment` for lighting. The PMREM step and the GPU upload therefore stay per-instance — but the *decode* no longer is: `loadHdrSource(src)` memoizes the loaded `DataTexture` per URL (sharing one in-flight promise, so N viewers appearing during one scroll trigger exactly one decode between them), and each call then wraps that one shared pixel buffer in a throwaway `DataTexture` purely so PMREM can upload it into *this* renderer's context, disposing the wrapper immediately after. Disposing a `DataTexture` frees the GPU copy and never the JS typed array behind it, so the cached source survives untouched. That removes N-1 fetches and, more importantly, N-1 RGBE→half-float decodes — tens of ms of main-thread work each, previously repeated once per grid card. A failed load evicts its own cache entry so a later viewer can retry rather than inherit a permanently-rejected promise. `loadEnvironment` returns the whole **`WebGLRenderTarget`**, not just its `.texture` — `PMREMGenerator` hands target ownership to the caller (`pmremGenerator.dispose()` frees only the generator's own scratch resources), so disposing the texture alone would strand the target's framebuffer. The `HDRLoader` call has a real error callback (logs + rejects) — without one, a failed HDRI request used to leave the returned promise neither resolved nor rejected, silently hanging `Promise.all([modelPromise, environmentPromise])` below forever with zero console output.
- `buildThreeViewer(product, metalKey, options)` — builds one viewer instance: `WebGLRenderer` + `Scene` + `PerspectiveCamera` + `TrackballControls`, a `ResizeObserver`-driven canvas that always exactly fills its container, a poster `<img>` (sourced from `product.assets["fallback-img"][metalKey]` — see `data.md`) shown until the model's first frame renders, and — layered on top of the base rotation — release inertia (frame-rate-independent, re-derived from a continuous decay rate rather than assumed-60fps, with an added progressive-braking boost at low speed so a coast stops crisply instead of trailing off), a continuous two-attractor up-vector leveling drift (fades to zero at the poles, flips sign continuously through the equator rather than snapping), a bezier/slerp-based "ease back to the default pose" idle reset, and a 3-phase idle "nudge" hint (a small camera wiggle synchronized with a floating hand-shaped overlay — a plain `<div>`, not an `<img>`, whose visible pixels come entirely from a `backdrop-filter: invert(1)` clipped to `assets/hand-pointer-thumb-opened.svg`'s silhouette used as a CSS mask, so it reads as a color-inverted cutout of whatever's underneath rather than a fixed-color icon; see `styling.md`) — suppressed session-wide via `sessionStorage["emjive_model_interacted"]` once any instance has actually been dragged (a real drag, not just a tap — same 6px-distance-threshold pattern `main.js`'s click-navigation uses). Returns `{ el, applyMetal(newKey), setCameraOrbit(orbitConfig), target, dispose() }` — `setCameraOrbit` is an instant (non-animated) reposition, used by the render harness (see `tooling.md`) and by `scene-tool.html`'s zoom/rotation/tilt fields; `target` (tool-only) is the live `controls.target` `Vector3` reference, needed to read a camera pose back as numbers (`scene-tool.html`'s whole reason for existing — nothing else in the codebase computes this inverse); `dispose()` tears down the animate loop/`ResizeObserver`/`TrackballControls`' own `window`-level key listeners, disposes the loaded model's own geometry/materials and the HDRI environment's PMREM texture (real GPU memory, tied to this renderer's context — not freed by `renderer.dispose()` alone), then calls `renderer.dispose()` followed by `renderer.forceContextLoss()` — the latter is what actually returns the WebGL context to the browser's finite per-page budget, since `renderer.dispose()` alone only frees the renderer's own bookkeeping (shader program cache, render lists), not the context itself. Originally `scene-tool.html`-only (builds-and-replaces a viewer every time its HDRI/model selection changes, and without a real teardown each switch leaked all three) — `main.js`'s grid now calls it too, repeatedly, as cards scroll in and out of `disposeObserver`'s range (see its own section below), which is exactly why the geometry/environment/context-loss teardown was added: the original renderer/controls-only version would have leaked exactly the GPU memory that lazy build/dispose scheme exists to cap. Returns `null` instead, without throwing, if the browser can't grant a WebGL context (a finite per-page budget — several simultaneous viewers, bfcache-retained contexts from earlier navigations, a weak/mobile GPU) — both `main.js` and `product.js` fall back to the plain `assets.icons[metalKey]` image in that case, same as a product with no `assets.model` field at all. Calls `controls.handleResize()` on every real resize (not just once at construction) — `TrackballControls` caches the element's screen rect itself rather than measuring fresh per pointer event, and at construction time the wrapper is still a detached `<div>` (the caller hasn't appended it to the page yet), so skipping this left `screen.width` permanently stuck at 0 and every drag silently a no-op (NaN rotation deltas, falsy, quietly skipped).
- `options.primitive` (tool/harness-only — `"cylinder"`/`"box"`/`"sphere"`/`"torus"`) — swaps the loaded GLTF for a bare `buildPrimitiveMesh()`-built mesh; everything downstream (`frameCamera()`'s bounding-sphere measurement, `applyMaterial()`'s mesh traversal, controls, the animate loop, `freeOrbit`, `dispose()`) is already agnostic to how `modelRoot` was built, so this is the only branch needed. `product` in this mode can be a minimal stub object — only `product["3d-viewer-camera-default"]`/`product.name`/`product.cameraTarget` are ever read, `product.assets` is never touched. Used by `scene-tool.html`'s swatch-scene mode and by `scripts/auto-render.js`'s swatch renderer (see `tooling.md`) — this **replaced** a separate `buildMaterialSwatch()` function that used to exist purely for that one purpose, retired once swatches needed the same draggable, savable camera orbit products already had (see `data.md`'s `swatch-camera`).
- `options.static` — harness-only (never set by the interactive site): skips the idle-nudge hint and the continuous per-frame animation loop entirely (only explicit `render()` calls, so nothing can shift the framing between the harness's `onReady` firing and its screenshot being taken a few ms later). `options.transparentBackground` — also harness-only, controls `preserveDrawingBuffer` (needed for an external screenshot readback of the canvas; the interactive site never reads its own canvas back). The renderer's alpha itself is unconditional now (both the interactive site and the harness render on a genuinely transparent canvas) — an earlier version kept the interactive site's canvas opaque on purpose to dodge a subtler ACES-tone-mapping edge-blending artifact, which traded it for a much more visible bug (a solid near-black square behind every model wherever the canvas wasn't covered by geometry).
- `options.freeOrbit` — `scene-tool.html`-only, wants the opposite trade-off from `static`: full interactive dragging (`static` never starts the animate loop at all, so a drag would be visually dead), but with release inertia and the idle-reset/leveling-drift/nudge behaviors above all switched off, so a dragged pose simply *stays* exactly where it's released rather than coasting or easing back — the whole point of a tool meant to let someone read a pose back as numbers. Three small, additive effects: sets `controls.staticMoving = true` (`TrackballControls`' own built-in "no momentum" flag, simpler than fighting the decay math that drives normal release inertia); skips arming the idle nudge (`scheduleIdleNudge()`'s guard); skips arming the "ease back to default" reset tween and the continuous up-vector leveling-drift correction (both gated individually inside the animate loop's normal-frame branch). `camera.lookAt(controls.target)` and the pole-crossing rotation itself (simply the *absence* of a polar clamp, not a separate mechanism — see below) are unaffected either way.

- `options.poster: false` / `options.maxPixelRatio` / `options.onReady` / `options.onError` — all four exist for `main.js`'s grid, where several viewers are alive at once. `poster: false` skips the built-in pre-load `<img>` entirely because the card already has its own image underneath doing that job; `maxPixelRatio` (1.5 on the grid, default 2 elsewhere) caps the canvas backing store, since **iOS Safari enforces a page-wide total canvas budget**, not a per-canvas one, and kills the tab once every canvas summed crosses it. `onReady`/`onError` fire once the model has loaded and painted, or once it definitively hasn't — the grid times its crossfade off the former and restores its static image on the latter. `onReady` predates both, added for `auto-render.js`'s screenshot timing.

### Teardown, and why it is load-bearing

`dispose()` is called constantly now — `main.js`'s grid disposes a card's viewer the moment it scrolls clear — so "was I torn down before this arrived?" is the normal case during a fast scroll, not an edge case. Three things this file gets right that are easy to regress:

1. **Both async load callbacks check `isDisposed` before touching anything**, and free what they were handed if it's set. A `.glb` arriving after teardown has its geometry disposed on the spot; a PMREM target likewise. Without that, a fast scroll leaked the full decoded geometry of everything it started but didn't finish, and — worse — the `Promise.all` ready path ran `renderer.render()` against a context `forceContextLoss()` had already killed, which is what filled the console with repeating `THREE.WebGLRenderer: Context Lost`.
2. **`dispose()` unregisters the viewer's `cancelNudge` from the module-level `allCancelNudgeFns` array, and removes its own `wrapper` pointer listeners.** Both are closures over the entire `buildThreeViewer()` invocation — renderer, scene, controls, decoded model — so either one left behind pins the whole viewer in memory no matter how diligently its GPU resources were freed. Measured on the Bones grid before this: **26 live `WebGLRenderer`s (and `Scene`s, and `TrackballControls`) retained after two scroll passes with zero viewers on screen**, growing linearly with every further pass. After: flat at whatever is actually visible. This is the kind of leak that reads as "iOS Safari reloads the page after a while" rather than as anything obviously wrong.
3. **`dispose()` is idempotent** — an early `if (isDisposed) return` — so a double dispose can't fire a second `forceContextLoss()` at a dead context.

### Render-on-demand

The animate loop ends in `drawIfChanged()`, not an unconditional `renderer.render()`. It compares the camera's current eye direction and up vector against the pose the canvas currently *shows*, and skips the draw when both are within `STILL_ANGLE_EPSILON` (1e-4 rad, ~0.006° — far below one pixel at any canvas size here). A `needsRender` flag covers the changes that aren't camera motion: a resize, and `applyMetal()`. The `rAF` loop itself keeps running (it's nearly free, and it's what notices a drag starting); only the WebGL draw is skipped. Before this, a viewer that had finished loading and was sitting perfectly still still issued a full draw 60+ times a second forever — on the homepage, for every live card at once, producing pixels identical to the ones already on screen. The epsilon is deliberately *smaller* than `SETTLE_ANGULAR_VELOCITY * dt`, so a release always registers as settled (arming the ease-back-to-default) **before** drawing stops; the other order would strand the camera wherever inertia happened to fade out.

Free, pole-crossing rotation (unlike the polar-angle-limited orbit a `<model-viewer>`-based approach would have) isn't a dedicated function either — it's the *absence* of any clamp on `TrackballControls`' own rotation. The extra code on top handles the *consequences* of that freedom: the up-vector leveling drift (so "up" doesn't visibly flip the instant a spin crosses a pole) and the slerp-based (not lerp+normalize) reset/nudge tweens (a naive lerp cuts a visually-wrong-speed chord for a large-angle/near-antipodal sweep, which a pole-crossing spin can easily leave the camera at).

**Exposes**: `window.EmjiveModelViewer = buildThreeViewer` — consumed by `main.js`'s grid, `product.js`'s carousel, and (with `options.freeOrbit`/`options.primitive`) `scene-tool.html`, a standalone dev tool outside the built site entirely (see `tooling.md`). Also `window.EmjiveModelViewer.METAL_PRESETS`, see above.

## `js/series.js` (~320 lines) — series resolution

Loaded blocking in `<head>` on every page (see above). Fetches `data/series.json` once and exposes `window.EmjiveSeries`:

- `ready` — a promise resolving to `{ index, slug, series }`. **Everything else on the site hangs off this**; `main.js`, `product.js` and `series-page.js` all start from it rather than fetching any JSON path themselves.
- `slug`/`series` — the ACTIVE series: `?series=` if it names a real one, else `index.featured`.
- `metals` — the global metal list. `categories()` — the active series' own category subset. `categoryInfo(id)` — that category's `{ sizes, unit }` from the global vocabulary.
- `loadProducts(slug)` / `loadManifest(slug)` — **memoized per slug**, so the grid and the hero handoff share one request.
- `mainHref` / `manifestHref` / `productHref` — URL builders. They deliberately **omit `?series=` for the featured series**, so everyday URLs stay clean and links bookmarked before the refactor keep resolving.
- `requestedSlug()` — the raw `?series=` with no fallback applied. Only `series.html` uses it, so it can show a not-found state instead of silently rendering the featured series' manifest.

It also owns **hero bundle loading** on `index.html` (guarded on `#seriesHero` existing): inject the preload hints, inject the hero stylesheet, fetch the fragment and inject the hero script — all in flight at once — then clone each `<template data-series-slot>` into its slot, call `EmjiveSeriesHero.init()`, and hand the series' products to `onProducts()`. On failure it strips `body.has-series-hero` so the selection bar isn't stranded off-screen. See `pages.md` for the full contract and the anti-flash reasoning.

`window.EmjiveHero` lives here too — a plain function registry (`onScroll`/`publishScroll`), not a `CustomEvent`, because it fires once per animation frame during scroll and a registry costs no allocation per publish.

`window.EmjiveMenus` also lives here — click-away coordination for the header menu (`main.js`) and the selection-bar drawer (`selection-bar.js`), two panels that don't know about each other and can be open at once. Each registers `{ root, close() }` via `opened(panel)`/`closed(panel)` when its own open state changes; `root` spans both the panel's trigger and its content, so clicking the trigger itself is never mistaken for "away". A single `document` click listener here closes only the most-recently-opened panel when a click lands outside every currently-open one's `root` — a second outside click is needed to close the other if both happened to be open together.

## `series/<slug>/hero.js` — one per series

The hero's behavior, loaded at runtime. Assigns `window.EmjiveSeriesHero = { init(root, ctx), onProducts(products) }` and does nothing else at execution time. For Bones that means the frontier-band lift, the scroll-driven x-ray wipe, and `updateHeroRings()` — one `.reveal__ring` `<img>` per product with `hero-hand-visibility.visible: true` (see `data.md`), each positioned/sized/rotated via inline custom properties set from that product's own `hero-hand-visibility` object, so multiple rings on screen don't fight over one shared set. It gets the **full, unfiltered** product list: the rings are hero art, not a listing.

Two rules any hero bundle has to keep: no side effects at execution time (the loader parallelizes on that assumption), and no bare specifiers (Vite never sees this file, so `import "three"` would ship unresolved — call `window.EmjiveModelViewer` instead).

## `js/main.js` (~400 lines)

Loads on **every** page. Owns:

- The header hamburger menu toggle. A delegated click handler on `.site-header__row` also toggles it from anywhere in the row's empty space — same as the `+`/`-` icon — while ignoring clicks on the brand logo (which navigates home instead) or on `.menu-toggle` itself (which already has its own listener, and would double-toggle otherwise). Registers a panel with `window.EmjiveMenus` (`js/series.js`) so a click away from the whole header closes it too — see that file's doc above.
- The **category filter row** (`renderHeaderFilter()`), rendered from `EmjiveSeries.categories()` — the active series' own subset — so it renders identically on pages that load no product data at all. Dual-purpose, branching on `filtersAreInPlace` (`!!document.getElementById("productGrid")`, true only on `index.html`): on the grid page it's the real filter (label + one `.is-cat` tag per category when there's more than one, a single inert `.is-active` tag with no `href` when there's exactly one, hidden outright at zero); everywhere else it's unconditionally a plain `.is-info` "Gallery" link back to `index.html#products` via `EmjiveSeries.mainHref()`. `syncFilterButtons()` toggles `.is-active`/`aria-current` on whichever tags are in `activeCats` — `css/style.css` turns that into a dot, not a color change, the same recipe size/metal selection uses elsewhere. The menu-close handler is **delegated** to the menu container, because those buttons are created after the script runs; a per-link listener would never reach them.
- **Filtering** (`applyFilter`/`toggleCategory`/`setCategories`), on the grid page only. Multi-select toggles that hide already-built cards, sync `?cat=` via `history.replaceState`, and leave the menu open so successive toggles are usable. Elsewhere the same buttons are ordinary links that navigate to the grid with one category applied. Unknown `?cat=` values are dropped against the active series' categories, so a typo shows everything rather than nothing.
- `wireModelClickNavigation(el, href)` — the 6px drag-distance-threshold click-vs-drag disambiguation, attached to a viewer's wrapper so rotating a model doesn't accidentally navigate. Wired inside `startViewerLoad` now (see below), at the point a card's viewer actually gets built, rather than unconditionally in `buildCard`. Tracks `activePointerId` so a `pointerup` that never had a matching `pointerdown` on this element — a drag begun on the page background and released over a card, or a second finger lifting during a two-finger scroll — is ignored rather than measured against stale (initially `0,0`) coordinates, which read as a zero-distance "click" and navigated to a product nobody tapped.
- The grid rendering (`buildCard`/`renderProducts`) — one card per product from `EmjiveSeries.loadProducts()`. Cards are built **once** and kept in a module-scope array; see the WebGL note in `pages.md` for why filtering must never rebuild them.
- **Lazy viewer build/dispose** (`buildViewerFor`/`disposeViewerFor`, two `IntersectionObserver`s) — `buildCard` no longer calls `window.EmjiveModelViewer` itself; it always builds the card's placeholder `<img>` first and returns `{ el, figure, iconEl, href }`, which `renderProducts` wraps into a `{ product, el, figure, iconEl, href, modelHandle, wantsViewer, queued, fadeTimer }` entry and hands to both observers (`figure.cardEntry = entry` is how each observer's callback finds its way back to that state). `buildObserver` (`rootMargin: "150px 0px 150px 0px"`) calls `buildViewerFor` once a card's figure nears the viewport; `disposeObserver` (`"300px 0px 300px 0px"` — deliberately larger, for hysteresis, so a card doesn't thrash build/dispose right at one boundary) calls `disposeViewerFor` once it's scrolled well clear. Falls back to eagerly building every viewer up front (the old behavior) if `IntersectionObserver` doesn't exist at all.
  **Which placeholder image, and why it isn't the icon.** The card shows `assets["fallback-img"][defaultMetal]` when the product has a model, falling back to `assets.icons[...]` only when it doesn't. These are **not** interchangeable: `auto-render.js` trims `icons` to their own alpha bounding box and rescales that to a fixed 80% of the frame (`ICON_CONTENT_FRACTION`) so thumbnails read consistently next to each other — deliberate, and exactly wrong here, because a thin ring's silhouette is far smaller than the bounding *sphere* `frameCamera()` fits to the viewport. Measured on Furcula: the icon drew the ring **1.232× larger** than the live model in both axes and re-centred it ~6% horizontally, so the handover read as the model snapping smaller and sideways the instant it appeared. `fallback-img` is the same capture saved *without* that treatment and matches the live canvas to **0.999× wide / 0.997× tall, centre within 0.1%** — i.e. invisibly. This is the whole reason `fallback-img` exists as a separate asset (see `assets.md`).
  **Load concurrency** (`MAX_CONCURRENT_MODEL_LOADS = 2`, `loadQueue`, `pumpLoadQueue`) — lazy building bounds how many viewers *exist*, not how many start loading at once, and a brisk scroll crosses every card's build margin within a second or two. Capping it means cards resolve one after another in the order they were scrolled past, rather than every model finishing late together with bandwidth split N ways. `entry.wantsViewer` (set by `buildObserver`, cleared by `disposeObserver`) lets `pumpLoadQueue` **drop** queued cards that scrolled back out before their turn came, instead of fetching a model nobody is looking at any more.
  **The crossfade** — the viewer is mounted at `opacity: 0` and faded in over `MODEL_FADE_MS` (400ms) from `onReady`; the placeholder is only taken out of the layout once that fade completes (hiding it mid-fade would show the page background through the model's transparent areas). `disposeViewerFor` clears that pending timer, so a card disposed mid-crossfade puts its image back correctly. Combined with `poster: false`, the card shows exactly one image at a time throughout.
  Exists because building every product's viewer — a `WebGLRenderer`, a full glTF fetch/decode, a from-scratch HDRI PMREM build, each — unconditionally and instantly the moment the grid rendered stopped being safe once the catalog grew past a handful of products: eight bones products at up to several tens of MB each meant eight simultaneous WebGL contexts, eight HDRI builds, and over 100MB of glTF data all at once on page load, reported as the page reloading erratically on scroll and crashing outright (Chrome's repeated-crash page) on real devices. Verified headlessly (a scripted scroll through the real page, not visual inspection): peak simultaneous viewers capped around 5 of 8 (was: all 8 instantly), zero models fetched before scrolling anywhere near the grid (was: ~100MB at page load), and a disposed card's viewer correctly rebuilds if scrolled back to.
  **`css/style.css`'s `.product-card__figure > img[hidden]` rule is load-bearing for this** — see `styling.md`. Toggling `.hidden` on the icon is a new use of that attribute here; without the matching CSS override, the base `img { display: block; }` rule (author-origin, beats the UA `[hidden]` regardless of specificity) left the "hidden" icon still laid out and pointer-interactive on top of the canvas, silently swallowing every drag meant for the model — confirmed via `elementsFromPoint` and `TrackballControls`' `_pointers` count staying 0 after a simulated `pointerdown`.
- A guarded contact-form stub (`getElementById("contactForm")`) — a no-op, since no page has that element. Kept for whenever a contact form gets built (see `procedures.md`).

Owns **no hero logic at all** any more, and no `METAL_PRESETS` or viewer-construction logic — those live in the active series' hero bundle and `js/three-viewer.js` respectively. `main.js` is purely a consumer of both.

## `js/selection.js` (126 lines)

The cart/selection data layer — a thin `localStorage` wrapper. `STORAGE_KEY = "emjive_selection"`. Read/write helpers fall back to `[]` on any error (e.g. corrupted JSON). Every mutating call dispatches `new CustomEvent("emjive:selection-changed")` on `window` — the sole mechanism other scripts use to react live to a change without a page reload.

Four mutators, all index-based (an item's position in the stored array, not an id): `addItem(item)` (pushes to the end), `removeItem(index)` (splices it out), `insertItem(index, item)` (splices it back in at a specific position — `launch-order.html`'s "Undo" after Unselect, so a restored item lands back where it was rather than at the end the way `addItem` would), and `updateItem(index, patch)` (`Object.assign`s `patch` onto the existing item in place — `launch-order.html`'s "Modify," changing metal/size and the price that comes with them without moving the item to the end the way remove+add would).

**Exposes**: `window.EmjiveSelection = { getSelection, addItem, removeItem, insertItem, updateItem, clear, formatPrice, appendSize }`. `appendSize(parent, size)` appends a size value to `parent` as plain text, except a decimal size's fractional part (e.g. `"59.43"`) — that renders in a `.size-fraction` span (`css/style.css`, `font-size: 0.75em`) instead of as a literal `.`, since every place a size is shown after selection (`selection-page.js`'s order rows, `selection-bar.js`'s drawer rows) already joins `.category.metal.size` with literal dots, and a decimal point in the size itself would read as a fourth trait segment.

**Item shape**: `{ series, productId, name, category, metal, size, price, image }` — a deliberately self-contained snapshot, so `launch-order.html` never has to re-fetch or join against any products file to render itself. `series` is what makes `productId` meaningful, since ids are only unique within one series. Selections saved before that field existed simply lack it; nothing here reads it, and `selection-bar.js`'s `itemKey()` tolerates it being absent so an existing cart doesn't read as all-new.

## `js/product.js` (~780 lines) — the largest file

Owns `product.html` end to end. Resolves `?id=` via `findProduct()` — the active series first, then a scan of the remaining series in index order (each memoized), which is what keeps bare `?id=` bookmarks working now that ids are only unique per series. Then renders (by the file's own numbered section comments):

1. **Label** — name, category, per-metal thumbnail, price.
2. **Carousel** — builds slides (a 3D viewer via `window.EmjiveModelViewer` if `product.assets.model` is set, else a fallback icon image, then any `product.assets.photos`). Each photo slide (`buildPhotoSlide()`, distinct from the plain `buildImageSlide()` the model-less fallback icon uses) also renders a `.product-carousel__caption` naming which finish/context that shot depicts — `"On display: " + (photo.description || "—")`. The caption is a real sibling of the `<img>`, not an overlay on top of it: it's absolutely positioned to the slide's own bottom-right corner, in extra height `css/style.css`'s `.product-carousel--has-photos` reserves below `--tile` on the viewport (toggled by `renderCarousel()` whenever `product.assets.photos` is non-empty) — done this way, rather than shrinking the photo's own box to fit a caption inside it, so every photo still fills `--tile` edge-to-edge and stays flush against its neighbors in the filmstrip. No rim/arrow click zones: navigation is either a free horizontal drag (rubber-band overshoot past either end; release lands exactly where the drag left it, clamped back into bounds — no momentum coast) or a tap directly on a slide, which centers it (`centerOnSlide()`) however far from center it started. On a narrow/phone-width viewport (`isMobileCarousel()` — reuses `css/style.css`'s one existing `max-width: 640px` breakpoint, the `.product-grid` one) a real drag instead always pages exactly one slide forward/backward and centers it, committing only past a real drag distance (15% of a tile) or a fast-enough short flick (gated by a minimum distance too, so touch-event jitter on a barely-moved drag can't read as a flick) — short/slow drags spring back to the slide they started on. A pointer's horizontal-vs-vertical intent is axis-locked in `onPointerMove` (the first movement past a small slop decides it, once) so a vertical scroll starting on the strip is handed off untouched to the browser's own `touch-action: pan-y` instead of the carousel eating part of the gesture; `pointercancel` (the browser interrupting a pointer itself — that same scroll handoff is the common case) is handled separately from a clean `pointerup` specifically so an interrupted gesture is never misread as a tap. Every way a slide gets centered shares one symmetric ease-in-out transition (`CENTER_TRANSITION`; `CANCEL_TRANSITION` is the same curve, shorter, used only when a mobile drag springs back without actually changing slides). Bounds stay "first/last tile centered" (not edge-flush). Carousel geometry can only be measured once `#productDetailContent` is actually visible (`[hidden]` elements measure zero) — bounds are explicitly re-synced right after the content is unhidden.
3. **Metal picker** — re-tints the live 3D model in place via `state.modelHandle.applyMetal(metal)` (no reload, no camera reset), and separately updates the label thumbnail/fallback icon/specs/price, since only the 3D model re-tints itself automatically.
4. **Characteristics** — metal-dependent weight/composition/price from `product["per-metal-specs"][selectedMetal]`.
5. **Select button + size modal** — sizes/units looked up by *category* (not per-product) via `EmjiveSeries.categoryInfo()`. Because that vocabulary is global rather than per-series, a cross-series hit needs no re-hydration. Standard-size buttons + a custom input capped at two decimal places (e.g. `"59.43"`) — a French (or other comma-decimal) mobile keypad's decimal key sends `,`, swapped to `.` before the digit filter runs, or it'd just get stripped. The confirm button (labeled plain "Add") is never actually `disabled` — clicking it with no size chosen instead crossfades its own label into a "First select a size" prompt for 2s (`.size-modal__confirm.is-nudging`, same opacity-crossfade recipe `.order-item__content`/`__overlay` use — see `styling.md`) rather than silently doing nothing. On confirm, calls `window.EmjiveSelection.addItem({...})` with the self-contained snapshot (including the resolved series) and closes the modal.

All page state lives in one `state` object (product, metals, selected metal/size, carousel scroll offset, the live model handle, etc.).

**Notable gotchas** (from the file's own comments): `img.draggable = false` + `dragstart` prevention stops the browser's native image-drag gesture from fighting the custom pointer-drag scroll; a `pointercancel` doesn't reliably carry the pointer's final coordinates, so settling a drag interrupted mid-gesture falls back to the strip's own live position instead of the event's `clientX`; a drag that starts on the 3D model slide is left alone entirely (no `pointerdown` tracking at all) so it rotates the model via `TrackballControls` instead of paging the carousel.

## `js/selection-bar.js` (~340 lines)

The floating bar shown on `index.html` and `product.html` only (not `launch-order.html` — that page isn't in its script list at all, plus it self-guards with `if (!window.EmjiveSelection) return;`). Builds its whole DOM programmatically and appends to `<body>`.

Shows either "No selected item" or a thumbnail strip + "Order ›" link; clicking the bar (not the Order link) opens a drawer with per-item "Unselect" rows. The drawer's `max-height` is set to a real measured pixel value in JS (not a CSS trick) — this is the piece `styling.md`'s drawer note points back to — specifically so it can animate smoothly both on open/close *and* on shrinking while already open (removing a row). `setDrawerOpen(isOpen)` is the one place that changes the drawer's open state — it also registers a panel with `window.EmjiveMenus` so a click away from the bar closes the drawer, same mechanism the header menu uses (see `js/series.js` above).

This file has no notion of **which page it's on**, which was always the point. It does now subscribe to `window.EmjiveHero.onScroll` for the homepage's scroll-driven entrance — but unconditionally: the active series' hero owns all the geometry and publishes how far past its trigger the page has scrolled, and this file measures its own `.selection-bar__summary` height to turn that into a transform. On a page with no hero nothing ever publishes, so nothing ever happens and the bar just stays visible — still zero special-casing. The starting-hidden state is `css/style.css`'s `body.has-series-hero` scoping (see `pages.md` for why that stopped being `:has()`).

Listens for `window.addEventListener("emjive:selection-changed", render)` — this is how it stays live-in-sync with additions from `product.js` or removals from its own drawer.

## `js/selection-page.js` (~690 lines) — `launch-order.html`'s checkout review

Grew enormously from a simple "list + total" renderer into the whole order page's logic: item rows with a Modify/Unselect overlay, per-row undo, a shipping pick, a terms toggle, and the checkout bar's gating — see `pages.md`'s `launch-order.html` section for what all of this actually looks like. `render()` (a full rebuild from `window.EmjiveSelection.getSelection()`) now only runs for the initial page load and after a Modify confirm — Unselect/Undo/the final timeout-collapse each mutate the DOM directly instead, so no row ever moves because of *another* row's undo window.

- **Item row overlay** — `openRowOverlay(li)`/`closeOpenRow()`, one open at a time (opening a new one closes whichever was already open). Mouse hover, a tap, or keyboard focus (`focusin`/`focusout`, chosen over `focus`/`blur` specifically because they bubble, so one delegated listener on the row covers both buttons inside it) all open the same overlay; a click landing elsewhere on an already-open row — anywhere but the Modify/Unselect buttons themselves — closes it back to the normal view instead of being ignored. Both are suppressed on a row that's mid-undo (`binding.pending`) — its overlay has nothing to show. `suppressHoverUntilMove` guards a real browser gotcha: a row's final collapse (`confirmRemoval`, below) reflows whatever's below it up the page, and if the cursor is just sitting still, whichever row's box slides underneath it fires a genuine, unrequested `pointerenter` — this flag makes any such "phantom" enter a no-op until an actual `pointermove` confirms the cursor moved on its own.
- **Per-row undo** (`rowBindings`, one `{ li, item, index, pending, timer, undoBtn }` per row, mirroring `itemsEl`'s children in order) — replaces an earlier shared-stack/shared-bar design. `handleUnselect(binding)` removes the item from storage immediately and crossfades that one row, *in place*, into its own "Undo" prompt (`.order-item__undo-prompt` — same `inset: 0` recipe `.order-item__overlay` uses, so nothing resizes or reflows) rather than collapsing it and showing a bar elsewhere; several rows can be independently mid-undo at once, each with its own `UNDO_TIMEOUT_MS` timer. `shiftIndices(binding, fromIndex, delta)` keeps every *other* binding's `.index` correct whenever one row's item is actually removed from or reinserted into storage, so each row always knows its true current position regardless of how many others are also pending or in what order they resolve — necessary because `EmjiveSelection.getSelection()` re-parses from `localStorage` on every call, so there's no stable object identity to key off instead. `handleUndo(binding)` reinserts at that live index and crossfades straight back — `.order-item__content` was only ever hidden, never rebuilt, so there's nothing to reload. If the window runs out unused, `confirmRemoval(binding)` finally collapses the row for real (`.order-item`'s `is-removing` class, `transitionend` on `max-height` with a 400ms reduced-motion fallback) — or, if `rowBindings` is left empty, skips that and crossfades the *whole list* directly into the empty state instead (`crossfadeToEmpty()`, a hand-orchestrated sequential opacity swap between `#selectionList` and `#selectionEmpty`, needed because `[hidden]` means `display: none`, which can't itself transition).
- **Modify** — `openModifyModal(item, index)` resolves `item.series` (falling back to `EmjiveSeries.slug` for a pre-refactor selection saved without one) and re-fetches that product via `EmjiveSeries.loadProducts()`, since the stored selection snapshot doesn't carry `per-metal-specs`/`icons`. The popup (`#modifyModal`) reuses `product.html`'s own `.size-modal`/`.product-metals` markup and CSS wholesale rather than a page-specific clone — a metal picker plus the standard/custom size picker, pre-filled to the item's current choice, wired almost identically to `product.js`'s `wireSelectButton()` — including the same custom-input two-decimal cap and comma-to-dot swap — except the static controls (input/guide toggle/backdrop/confirm/Escape) are wired exactly once and read a mutable `modifyState` object rather than closing over one fixed product, since a different row's item can sit behind this same modal on each open. Unlike "Add," "Save" (`modifyModalConfirm`) still just toggles `.disabled` directly and has no nudge — a pre-filled item always has *some* size going in, so it's never expected to actually need one. Confirms via `window.EmjiveSelection.updateItem()`, recomputing price from the newly-selected metal's `per-metal-specs`, then a full `render()` — which silently ends any *other* row's still-pending undo early, since that rebuild repopulates straight from current storage with no way to carry mid-flight per-row state across it. Rare enough (needs two different rows mid-interaction at once) not to be worth engineering around.
- **Shipping/terms/checkout** — `SHIPPING_OPTIONS`, a small in-file placeholder array (easy to extend later, not a restructure), rendered as a single-select dot-indicator list. The terms row's click is delegated across the whole element (the dedicated tick-box or the surrounding sentence both toggle; a click on the actual `<a>` to `terms.html` navigates instead — same "toggle vs. its own separately-clickable label" split `selection-bar.js`'s drawer toggle/empty-label pair uses). `updateCheckoutGate()` disables `#orderCheckoutButton` until both a shipping option is selected and terms are ticked. The button itself is a stub — no Stripe session exists yet, so a click (once enabled) just `alert()`s that it isn't connected, the same convention `main.js`'s guarded `#contactForm` handler uses.

## Cross-cutting contracts (the highest-value section if you're changing behavior that spans files)

- **`window.EmjiveSeries`** — set by `js/series.js` (blocking, in `<head>`), consumed by `main.js`, `product.js` and `series-page.js`. The one place "which series is this, and where's its data" lives.
- **`window.EmjiveHero`** — set by `js/series.js`, published to by the active series' `hero.js`, subscribed to by `selection-bar.js`. A plain function registry, one number: how far past the hero's trigger point the page has scrolled.
- **`window.EmjiveMenus`** — set by `js/series.js`, registered with by `main.js` (header menu), `selection-bar.js` (drawer), and `selection-page.js` (each item row's Modify/Unselect overlay, one at a time). Click-away coordination: a click outside every currently-open panel's root closes only the most-recently-opened one.
- **`window.EmjiveSeriesHero`** — set by a series' `hero.js`, called by `js/series.js`. `{ init(root, ctx), onProducts(products) }`.
- **`window.EmjiveModelViewer`** — set by `three-viewer.js`, consumed by `main.js` (grid), `product.js` (carousel), and `scene-tool.html` (a standalone dev tool, `options.freeOrbit`/`options.primitive`). The one place 3D viewer construction/materials/camera behavior lives.
- **`window.EmjiveSelection`** — set by `selection.js`, consumed by `product.js` (add), `selection-bar.js` (add/remove/read, plus `appendSize` for its own row display), `selection-page.js` (remove/insert/update/read, plus `appendSize`).
- **`"emjive:selection-changed"`** — `CustomEvent` on `window`, dispatched by every `selection.js` mutation. Only `selection-bar.js` listens for it.
- **`localStorage["emjive_selection"]`** — the persisted selection array (via `selection.js`).
- **`sessionStorage["emjive_model_interacted"]`** — unrelated to selection; remembers within a browsing session whether the visitor has already discovered models are draggable, to stop nudging them with the wiggle hint (set/read in `three-viewer.js`).
- **Item shape**: `{ series, productId, name, category, metal, size, price, image }` (see `selection.js` above).

## `js/series-page.js` (~55 lines)

`series.html` only. Resolves the slug via `EmjiveSeries.requestedSlug()` — deliberately **not** the fallback-applying `.slug` — loads that series' manifest, fills in the title/year/subtitle, and otherwise shows a not-found state. Rendering `manifest.json`'s `sections[]` belongs here later; the page is an empty shell by design.
