# Client-side scripts

`js/` has 10 files, plus per-series hero bundles under `series/<slug>/`. 9 are plain classic scripts (`<script>` tags, no bundler needed to ship them). The 10th, `js/three-viewer.js`, is an ES module (`<script type="module">`, loaded from `<head>`) — it needs to `import` the `three` npm package, which only a module script can do. Despite the different script *kind*, it's fully part of the live site, not a dev-only file — see `tooling.md` for why an ES module is safe to mix into an otherwise-classic-script codebase, and `pages.md` for the exact load-order mechanics.

## Load order (see `pages.md` for the full page × script matrix and the `defer`/blocking explanation)

`js/series.js` is blocking in `<head>` on every page, so `window.EmjiveSeries` and `window.EmjiveHero` exist before anything else runs — including `launch-order.html`'s plain synchronous `main.js`. `selection.js` always loads before anything that touches `window.EmjiveSelection`. `three-viewer.js` (a module, in `<head>`) always finishes before `main.js`/`product.js` (both `defer`), the only two classic scripts that touch `window.EmjiveModelViewer` directly.

A series' `hero.js` loads later still — injected at runtime by `series.js` — which is why it's written to be inert until called.

`index.html` alone also loads `js/product-focus.js` then `js/lens-artefact.js`, both `defer`, both after `main.js`/`selection.js`/`selection-bar.js` in document order. That relative order matters once: `lens-artefact.js` subscribes to `window.EmjiveFocus`, which `product-focus.js` is what defines, so it has to run second. Neither depends on `three-viewer.js` finishing first in the way `main.js` used to — see that file's own section below for why the grid no longer touches `window.EmjiveModelViewer` at all.

## `js/three-viewer.js` (~970 lines) — the 3D viewer

The single shared construction path for every 3D product view on the site (the homepage lens's one reused viewer, the product-detail carousel) and for `scripts/auto-render.js`'s render pipeline — see `tooling.md`. A raw three.js scene per instance, driven by the `TrackballControls` addon (free, pole-crossing rotation — unlike the polar-angle-limited orbit a `<model-viewer>`-based approach would have), with a substantial amount of hand-tuned polish layered on top. Exports (all module-internal except the one exposed global):

- `METAL_PRESETS` — PBR values (`baseColorFactor`/`metallicFactor`/`roughnessFactor`) per metal name, the single source of truth repo-wide (also reused by `scripts/auto-render.js`'s harness, since it loads this exact module). Must stay in sync with `data/series.json`'s top-level `metals` list — see `procedures.md`'s "adding a metal" checklist. `metalToStandardMaterialParams()` converts a preset to `THREE.MeshStandardMaterial` params. Also exposed live as `window.EmjiveModelViewer.METAL_PRESETS` (tool-only — `main.js`/`product.js` never read it) — `applyMetal()` and every viewer build already re-read `METAL_PRESETS[metalKey]` fresh on every call, so `scene-tool.html`'s shader-tuning sliders just mutate this object in place and re-invoke `applyMetal()`/rebuild to preview a change instantly, with no separate override-parameter path needed.
- `parseOrbitConfig()` / `parseTargetString()` — parse `product["3d-viewer-camera-default"]`'s `{ rotation, tilt, zoom }` object (descriptive names for what used to be a single `"<theta>deg <phi>deg <radius%>"` string, the convention a `<model-viewer camera-orbit>` attribute would have used) / `cameraTarget`'s `"Xm Ym Zm"` string format into the radians/percent the camera-framing math needs.
- `loadEnvironment(renderer, hdriSrc)` — loads + PMREM-converts an HDRI into an environment map. `hdriSrc` is the caller-resolved path (`data/series.json`'s top-level `hdris` map, looked up via a series' own `hdri` key by `js/series.js`'s `hdriPath()`, or `scripts/auto-render.js`'s own equivalent resolution — see `data.md`); an omitted/unresolved value falls back to the module's own `DEFAULT_HDRI_SRC` (still `studio_kontrast_04_2k.hdr`) — this module is deliberately series-unaware, and `auto-render.js`'s headless harness never loads `js/series.js` at all, so it can't resolve a key here either way. Rebuilt fresh for every `buildThreeViewer()` call, never cached/shared across instances despite two viewers often resolving to the same file (any two showing series that picked the same `hdris` key): a PMREM texture is a GPU resource tied to the specific `WebGLRenderer`/context that built it, and each instance has its own renderer. An earlier version cached this at module scope, meant to be reused across the homepage grid's several simultaneous viewers — that handed later instances a texture handle from a different (invalid) context, which silently rendered them solid black, since this scene has zero `THREE.Light` objects and depends entirely on `scene.environment` for lighting. Loading it per-instance costs a redundant fetch+decode+PMREM-generate per grid card, but normal HTTP caching keeps the repeat fetches cheap. The `HDRLoader` call has a real error callback (logs + rejects) — without one, a failed HDRI request used to leave the returned promise neither resolved nor rejected, silently hanging `Promise.all([modelPromise, environmentPromise])` below forever with zero console output.
- `buildThreeViewer(product, metalKey, options)` — builds one viewer instance: `WebGLRenderer` + `Scene` + `PerspectiveCamera` + `TrackballControls`, a `ResizeObserver`-driven canvas that always exactly fills its container, a poster `<img>` (sourced from `product.assets["fallback-img"][metalKey]` — see `data.md`) shown until the model's first frame renders, and — layered on top of the base rotation — release inertia (frame-rate-independent, re-derived from a continuous decay rate rather than assumed-60fps, with an added progressive-braking boost at low speed so a coast stops crisply instead of trailing off), a continuous two-attractor up-vector leveling drift (fades to zero at the poles, flips sign continuously through the equator rather than snapping), a bezier/slerp-based "ease back to the default pose" idle reset, and a 3-phase idle "nudge" hint (a small camera wiggle synchronized with a floating hand-shaped overlay — a plain `<div>`, not an `<img>`, whose visible pixels come entirely from a `backdrop-filter: invert(1)` clipped to `assets/hand-pointer-thumb-opened.svg`'s silhouette used as a CSS mask, so it reads as a color-inverted cutout of whatever's underneath rather than a fixed-color icon; see `styling.md`) — suppressed session-wide via `sessionStorage["emjive_model_interacted"]` once any instance has actually been dragged (a real drag, not just a tap — same 6px-distance-threshold pattern `main.js`'s click-navigation uses). Returns `{ el, applyMetal(newKey), setCameraOrbit(orbitConfig), target, dispose() }` — `setCameraOrbit` is an instant (non-animated) reposition, used by the render harness (see `tooling.md`) and by `scene-tool.html`'s zoom/rotation/tilt fields; `target` (tool-only) is the live `controls.target` `Vector3` reference, needed to read a camera pose back as numbers (`scene-tool.html`'s whole reason for existing — nothing else in the codebase computes this inverse); `dispose()` (tool-only) tears down the animate loop/`ResizeObserver`/`TrackballControls`' own `window`-level key listeners — every other caller builds exactly one, page-lifetime viewer and never calls it, but `scene-tool.html` builds-and-replaces one every time its HDRI/model selection changes, and without a real teardown each switch would leak all three. Returns `null` instead, without throwing, if the browser can't grant a WebGL context (a finite per-page budget — several simultaneous viewers, bfcache-retained contexts from earlier navigations, a weak/mobile GPU) — both `main.js` and `product.js` fall back to the plain `assets.icons[metalKey]` image in that case, same as a product with no `assets.model` field at all. Calls `controls.handleResize()` on every real resize (not just once at construction) — `TrackballControls` caches the element's screen rect itself rather than measuring fresh per pointer event, and at construction time the wrapper is still a detached `<div>` (the caller hasn't appended it to the page yet), so skipping this left `screen.width` permanently stuck at 0 and every drag silently a no-op (NaN rotation deltas, falsy, quietly skipped).
- `options.primitive` (tool/harness-only — `"cylinder"`/`"box"`/`"sphere"`/`"torus"`) — swaps the loaded GLTF for a bare `buildPrimitiveMesh()`-built mesh; everything downstream (`frameCamera()`'s bounding-sphere measurement, `applyMaterial()`'s mesh traversal, controls, the animate loop, `freeOrbit`, `dispose()`) is already agnostic to how `modelRoot` was built, so this is the only branch needed. `product` in this mode can be a minimal stub object — only `product["3d-viewer-camera-default"]`/`product.name`/`product.cameraTarget` are ever read, `product.assets` is never touched. Used by `scene-tool.html`'s swatch-scene mode and by `scripts/auto-render.js`'s swatch renderer (see `tooling.md`) — this **replaced** a separate `buildMaterialSwatch()` function that used to exist purely for that one purpose, retired once swatches needed the same draggable, savable camera orbit products already had (see `data.md`'s `swatch-camera`).
- `options.static` — harness-only (never set by the interactive site): skips the idle-nudge hint and the continuous per-frame animation loop entirely (only explicit `render()` calls, so nothing can shift the framing between the harness's `onReady` firing and its screenshot being taken a few ms later). `options.transparentBackground` — also harness-only, controls `preserveDrawingBuffer` (needed for an external screenshot readback of the canvas; the interactive site never reads its own canvas back). The renderer's alpha itself is unconditional now (both the interactive site and the harness render on a genuinely transparent canvas) — an earlier version kept the interactive site's canvas opaque on purpose to dodge a subtler ACES-tone-mapping edge-blending artifact, which traded it for a much more visible bug (a solid near-black square behind every model wherever the canvas wasn't covered by geometry).
- `options.freeOrbit` — `scene-tool.html`-only, wants the opposite trade-off from `static`: full interactive dragging (`static` never starts the animate loop at all, so a drag would be visually dead), but with release inertia and the idle-reset/leveling-drift/nudge behaviors above all switched off, so a dragged pose simply *stays* exactly where it's released rather than coasting or easing back — the whole point of a tool meant to let someone read a pose back as numbers. Three small, additive effects: sets `controls.staticMoving = true` (`TrackballControls`' own built-in "no momentum" flag, simpler than fighting the decay math that drives normal release inertia); skips arming the idle nudge (`scheduleIdleNudge()`'s guard); skips arming the "ease back to default" reset tween and the continuous up-vector leveling-drift correction (both gated individually inside the animate loop's normal-frame branch). `camera.lookAt(controls.target)` and the pole-crossing rotation itself (simply the *absence* of a polar clamp, not a separate mechanism — see below) are unaffected either way.
- `handle.loadProduct(nextProduct, nextMetalKey)` / `handle.returnToDefaultPose(durationMs)` — added for `js/lens-artefact.js`, the homepage lens's one reused viewer (see that file's own doc): every earlier caller builds exactly one, page-lifetime viewer, but the lens changes which product it shows on every scroll step, and building a fresh `WebGLRenderer` each time cost a full HDR decode + PMREM regeneration per step (~180ms of blocked main thread, a dropped frame mid-snap) — a PMREM texture is tied to the specific context that built it (see `loadEnvironment`'s own note above), so the only way to stop paying for it repeatedly is to stop making renderers. `loadProduct()` swaps a different product's model into the SAME renderer/context/environment map: re-reads `defaultOrbit`/`explicitTarget`/`currentMetal` from the new product, disposes the outgoing `modelRoot`'s geometry/materials, loads the new GLB, re-applies material and `frameCamera()`. Returns a promise resolving `true` once painted, `false` if there's nothing to load or the viewer's since been disposed. `returnToDefaultPose(durationMs)` starts the exact same slerp-based reset tween the idle timer arms (`resetTweenActive`/`resetTweenFromPosition`/etc. — same variables, same animate-loop branch), just immediately and over a caller-chosen duration instead of waiting for release-inertia to decay naturally first. Both call the new `clearControlsMomentum()` helper (`controls._lastAngle = 0; controls._movePrev.copy(controls._moveCurr)`) — `TrackballControls` tracks its own internal release-inertia accumulator (`_lastAngle`/`_lastAxis`, decayed and re-applied on every `controls.update()` call — entirely separate from this file's own `lastAngularSpeed` bookkeeping, and untouched by the addon's own `reset()` method, which only restores the pose captured at construction). The pre-existing idle-triggered reset never needed to clear it, because it only arms once its own angular-velocity check confirms momentum has *already* decayed to near-nothing first; `returnToDefaultPose()`'s callers offer no such guarantee — a focus change can interrupt a fast spin at full speed — and a reused controls instance left uncleared would carry that stale momentum into whichever product loads next, visibly spinning it with the previous product's leftover motion.

Free, pole-crossing rotation (unlike the polar-angle-limited orbit a `<model-viewer>`-based approach would have) isn't a dedicated function either — it's the *absence* of any clamp on `TrackballControls`' own rotation. The extra code on top handles the *consequences* of that freedom: the up-vector leveling drift (so "up" doesn't visibly flip the instant a spin crosses a pole) and the slerp-based (not lerp+normalize) reset/nudge tweens (a naive lerp cuts a visually-wrong-speed chord for a large-angle/near-antipodal sweep, which a pole-crossing spin can easily leave the camera at).

**Exposes**: `window.EmjiveModelViewer = buildThreeViewer` — consumed by `js/lens-artefact.js` (the homepage's one reused viewer, `loadProduct()`/`returnToDefaultPose()` above), `product.js`'s carousel, and (with `options.freeOrbit`/`options.primitive`) `scene-tool.html`, a standalone dev tool outside the built site entirely (see `tooling.md`). **Not** `main.js` any more — the grid itself builds no viewer at all, see that file's own section below. Also `window.EmjiveModelViewer.METAL_PRESETS`, see above.

## `js/series.js` (~320 lines) — series resolution

Loaded blocking in `<head>` on every page (see above). Fetches `data/series.json` once and exposes `window.EmjiveSeries`:

- `ready` — a promise resolving to `{ index, slug, series }`. **Everything else on the site hangs off this**; `main.js`, `product.js` and `series-page.js` all start from it rather than fetching any JSON path themselves.
- `slug`/`series` — the ACTIVE series: `?series=` if it names a real one, else `index.featured`.
- `metals` — the global metal list. `categories()` — the active series' own category subset. `categoryInfo(id)` — that category's `{ sizes, unit }` from the global vocabulary.
- `loadProducts(slug)` / `loadManifest(slug)` — **memoized per slug**, so the grid and the hero handoff share one request.
- `mainHref` / `manifestHref` / `productHref` — URL builders. They deliberately **omit `?series=` for the featured series**, so everyday URLs stay clean and links bookmarked before the refactor keep resolving.
- `requestedSlug()` — the raw `?series=` with no fallback applied. Only `series.html` uses it, so it can show a not-found state instead of silently rendering the featured series' manifest.

It also owns **hero bundle loading** on `index.html` (guarded on `#seriesHero` existing): inject the preload hints, inject the hero stylesheet, fetch the fragment and inject the hero script — all in flight at once — then clone each `<template data-series-slot>` into its slot, call `EmjiveSeriesHero.init()`, and hand the series' products to `onProducts()`. On failure it strips `body.has-series-hero` so the selection bar isn't stranded off-screen. See `pages.md` for the full contract and the anti-flash reasoning.

`window.EmjiveHero` lives here too — a plain function registry (`onScroll`/`publishScroll`), not a `CustomEvent`, because it fires once per animation frame during scroll and a registry costs no allocation per publish.

`window.EmjiveMenus` also lives here — click-away coordination for the header menu (`main.js`) and the selection-bar drawer (`selection-bar.js`), two panels that don't know about each other and can be open at once. Each registers `{ root, close() }` via `opened(panel)`/`closed(panel)` when its own open state changes; `root` spans both the panel's trigger and its content, so clicking the trigger itself is never mistaken for "away". A single `document` click listener here closes only the most-recently-opened panel when a click lands outside every currently-open one's `root` — a second outside click is needed to close the other if both happened to be open together.

## `series/<slug>/hero.js` — one per series

The hero's behavior, loaded at runtime. Assigns `window.EmjiveSeriesHero = { init(root, ctx), onProducts(products) }` and does nothing else at execution time. For Bones that means the frontier-band lift, the scroll-driven x-ray wipe, and `updateHeroRings()` — one `.reveal__ring` `<img>` per product with `hero-hand-visibility.visible: true` (see `data.md`), each positioned/sized/rotated via inline custom properties set from that product's own `hero-hand-visibility` object, so multiple rings on screen don't fight over one shared set. It gets the **full, unfiltered** product list: the rings are hero art, not a listing.

Two rules any hero bundle has to keep: no side effects at execution time (the loader parallelizes on that assumption), and no bare specifiers (Vite never sees this file, so `import "three"` would ship unresolved — call `window.EmjiveModelViewer` instead).

## `js/main.js` (~420 lines)

Loads on **every** page. Owns:

- The header hamburger menu toggle. A delegated click handler on `.site-header__row` also toggles it from anywhere in the row's empty space — same as the `+`/`-` icon — while ignoring clicks on the brand logo or on `.menu-toggle` itself (which already has its own listener, and would double-toggle otherwise). Registers a panel with `window.EmjiveMenus` (`js/series.js`) so a click away from the whole header closes it too — see that file's doc above.
- **The brand logo's own click handler**, separate from the menu-toggle delegation above. Checked at click time (not at attach time — `main.js` is the first `defer`red script to run, before `product-focus.js` has defined anything): if `window.EmjiveFocus.goHome` exists (`index.html` only), the click is intercepted (`preventDefault`) and handed to it instead of the plain `href="#top"` anchor — see `product-focus.js`'s own section below for what that does. Everywhere else the brand link is a real cross-page navigation (`href="index.html#top"`), `window.EmjiveFocus` never exists, and the native click goes through untouched.
- The **category filter row** (`renderHeaderFilter()`), rendered from `EmjiveSeries.categories()` — the active series' own subset — so it renders identically on pages that load no product data at all. Dual-purpose, branching on `filtersAreInPlace` (`!!document.getElementById("productGrid")`, true only on `index.html`): on the grid page it's the real filter (label + one `.is-cat` tag per category when there's more than one, a single inert `.is-active` tag with no `href` when there's exactly one, hidden outright at zero); everywhere else it's unconditionally a plain `.is-info` "Gallery" link back to `index.html#products` via `EmjiveSeries.mainHref()`. `syncFilterButtons()` toggles `.is-active`/`aria-current` on whichever tags are in `activeCats` — `css/style.css` turns that into a dot, not a color change, the same recipe size/metal selection uses elsewhere. The menu-close handler is **delegated** to the menu container, because those buttons are created after the script runs; a per-link listener would never reach them.
- **Filtering** (`applyFilter`/`toggleCategory`/`setCategories`), on the grid page only. Multi-select toggles that hide already-built cards, sync `?cat=` via `history.replaceState`, and leave the menu open so successive toggles are usable. Elsewhere the same buttons are ordinary links that navigate to the grid with one category applied. Unknown `?cat=` values are dropped against the active series' categories, so a typo shows everything rather than nothing.
- The grid rendering (`buildCard`/`renderProducts`) — one card per product from `EmjiveSeries.loadProducts()`, each a plain `<img>` now (`product.assets["fallback-img"][metal]`, falling back to `.icons`) rather than a 3D viewer. `fallback-img` specifically, not `icons`: it's the model's own default-orbit capture as-is, whereas `icons` is cropped/re-centered for flat-thumbnail use elsewhere — using it here is what lets `js/lens-artefact.js`'s magnification read as an honest, known factor rather than an arbitrary reframe (see that file's own doc). The grid itself builds **zero** WebGL contexts any more — `wireModelClickNavigation()` (the 6px drag-vs-click disambiguation) moved to `lens-artefact.js` along with the one viewer it now guards, since that's the only place on the page anything still rotates. Cards are built **once**, kept in a module-scope array paired with their product; `applyFilter()` still only ever toggles `card.hidden`, never rebuilds, for the same reason as before minus the WebGL angle — `js/product-focus.js` re-derives the currently-visible/focused card from this same array on every change, and rebuilding would drop that state.
- Every call to `applyFilter()` (the initial render included) publishes `window.EmjiveGrid = { entries: cards }` and dispatches `"emjive:grid-changed"` on `window` — the one funnel `js/product-focus.js` and `js/lens-artefact.js` both key off to learn which cards are currently visible. Published as state *and* an event, not just an event: this runs inside `loadProducts()`'s own `.then()`, and on a warm cache that promise can resolve in the gap between two `defer`red scripts, before the later one has even executed far enough to subscribe — a late reader finds `window.EmjiveGrid` sitting there instead of having missed the one-time event.
- A guarded contact-form stub (`getElementById("contactForm")`) — a no-op, since no page has that element. Kept for whenever a contact form gets built (see `procedures.md`).

Owns **no hero logic at all** any more, and no `METAL_PRESETS` or viewer-construction logic — those live in the active series' hero bundle and `js/three-viewer.js` respectively. `main.js` is purely a consumer of both — now more so than ever, since it no longer even calls `window.EmjiveModelViewer`.

## `js/product-focus.js` (~680 lines) — grid snap-scroll + focus

`index.html` only (self-guards on `#productGrid`). Turns the grid into a one-item-per-gesture filmstrip: every scroll step settles exactly one product's card center on the viewport's center, which is where the fixed lens sits (see `styling.md`'s Lab-lens section). Every handler no-ops above `targetScrollFor(0)`, so the hero's own multi-viewport scroll-driven wipe stays freely scrubbable — but the strip's own top edge isn't a plain hand-back to the browser any more: scrolling up off the first product now snaps to the hero boundary (`goToHero()`/`heroTargetScroll()`, below) rather than releasing to free scroll, mirroring how an arrival from the hero already snaps onto that same first product.

**Exposes `window.EmjiveFocus`**: `onChange(fn)` (fires the moment focus changes — the strip *starting* to move — and hands a late subscriber the current value immediately on registering, same "plain registry, not a `CustomEvent`" shape `window.EmjiveHero` uses, for the same per-frame-cost reason), `onSettled(fn)` (fires once the strip has actually stopped on that product), `entries()` (the currently-visible `[{ product, el }]` list), `goHome()` (cancels any in-flight snap, drops a pending `sessionStorage` restore so a later settle can't drag the page back down, and animates to the very top of the page — `js/main.js`'s brand-logo click handler is the one caller, see its own section above).

**The snap tween** is hand-animated (`requestAnimationFrame` + `window.scrollTo({behavior:"instant"})`), not native `scrollTo({behavior:"smooth"})` — the native one exposes neither duration nor easing, and its pace is too brisk for a product easing in under a lens. A cubic Hermite spline (`hermiteEaseTo1`) lets a snap **inherit an already-moving scroll's velocity** instead of always starting from a standing stop, used only for the two "taking over a scroll already in motion" cases (`runCapture`'s mid-fling catch, and `onSettle`'s correction on arrival from the hero) — a deliberate single-gesture step keeps a plain `easeInOutCubic` start-from-rest, which is the correct feel for a discrete "go to next" command. The incoming tangent is clamped to 2 — verified numerically (not just asserted) monotone and non-overshooting up to ~3 before the curve dips. `goHome()` and `goToHero()` (below) both use this same standing-start tween, just targeting `0`/`heroTargetScroll()` instead of a card.

**Four-way gesture handling** (`gestureMode(direction)`): `"free"` (still in the hero itself — index is `-1`, already released — hand it to the browser untouched), `"hero"` (scrolling up off the first product — snap to the hero boundary via `goToHero()` rather than releasing), `"absorb"` (past the last product — swallow the gesture rather than let the page drift into empty run-off and rubber-band back), `"advance"` (move one product). Wheel, touch and keyboard (arrow/`PageUp`/`PageDown`/space) all funnel through this one function.

**`heroTargetScroll()`** solves for the scrollY that puts `#seriesHero`'s bottom edge on the viewport's vertical middle — the same boundary `js/lens-artefact.js`'s `syncGlass()` already tests live (that file's own comment frames crossing it upward as "scrolling back up toward the x-ray hand"), just solved for a scroll position instead of read as a live true/false. Deliberately reuses that already-established, series-agnostic measurement rather than reaching for a series-specific element (an actual x-ray hand id) a future series' hero might not even have.

**`runCapture()` exists alongside the debounced settle for a scroll-latching reason**: once a fling has begun scrolling the document, Chrome stops honoring `preventDefault()` on the rest of that gesture's wheel events — a flick started in the hero carries straight through the whole strip untouched unless something grabs it mid-scroll. `runCapture` runs on every scroll frame (throttled to one `requestAnimationFrame` per real scroll event) and re-centers the nearest product once drift exceeds a third of a card's height, or immediately if nothing is focused yet (the latched-fling-into-an-empty-strip case).

**Position persistence** (`sessionStorage["emjive_grid_position"]`) — the focused product's `id` plus the active series slug are saved on `pagehide`; restored via a plain `jumpTo` (not the tween — "instantly come back to this point" is the whole point) the moment a matching entry exists. Deliberately **sticky, not one-shot**: re-tried on every settle opportunity — including the hero-bundle-landed corrections `js/series.js`'s async fetches trigger later — until either a real gesture clears it (`clearPendingRestore()`, called from all four gesture-handling sites, never from the restore's own internal jump) or it lands. A one-shot attempt right at page load would race the hero bundle, which starts as a single reserved viewport (`.series-hero { min-height: 100svh }`, see `pages.md`) and only reaches its real several-viewport height once its own stylesheet actually arrives — computing a scroll target against that placeholder height would jump to the wrong place.

**`window.EmjiveGrid`** (set by `js/main.js`, see its own section above) is read directly at script init, alongside the normal `"emjive:grid-changed"` listener — the warm-cache race that state exists to cover.

## `js/lens-artefact.js` (~647 lines) — the lab-lens

`index.html` only (self-guards on `#lensArtefact`). Owns all three fixed layers of the physical lens overlay (see `styling.md`'s Lab-lens section for the CSS): the glass render, the magnified view inside it, and the sliding label bar. Two independent inputs:

- **`window.EmjiveFocus`** (`js/product-focus.js`) — drives the magnified viewer and the label, and is the glass's own real forward trigger too: `onChange` fires the instant `product-focus.js`'s own snap-to-first-item tween starts ("Focus changes up front, not on arrival" is that file's own wording for it), which is what `enterGrid()` paces the glass's extend against — see below.
- **The hero's own geometry**, measured directly off `#seriesHero`'s `getBoundingClientRect().bottom` — a fallback forward trigger for a grid with zero visible products (where `EmjiveFocus` never fires a real one), and the sole, authoritative trigger for the *reverse*. Deliberately **not** `window.EmjiveHero`: that number is calibrated to a different moment (the frontier band clearing the fixed header), which fires while the hero's x-ray reveal still fills the screen — keying the lens to it made the glass appear over the hero artwork. The hero's bottom edge crossing the screen's vertical middle is symmetric for free, so scrolling back up retracts the glass again at exactly the point it appeared.

**The glass plays a hand-authored 60-frame extend/retract sequence**, not a plain opacity fade (`assets/lab-lens-frames/lab-lens_01.webp`…`_59.webp`, frame 60 being `assets/lab-lens.webp` itself — see `assets.md`; re-rendered once already, and now exported directly to WebP rather than converted from PNG). All 60 frames are preloaded eagerly and unconditionally the instant this script runs (plain `Image()` objects, not `<link rel=preload>` — deliberately not competing with the hero's own critical preloads for bandwidth this sequence doesn't need until well into the scroll). Playback (`playGlass(target, durationMs, onComplete)`) is a `requestAnimationFrame`-driven `src` swap between frames over real time; a fresh call always supersedes one already in flight via a token bump (`glassToken`, the same idiom `loadToken` below uses for a stale glTF load), so a crossing that reverses direction mid-animation resumes from the current frame rather than restarting or jumping.

**The forward entrance plays the whole 1 → 60 span in one go** (`enterGrid()`), paced to `product-focus.js`'s own snap-to-first-item tween rather than to the clip's raw length: the full span plays at whatever rate makes it take exactly `SNAP_DURATION_MS` — 850ms, hand-mirrored from `product-focus.js`'s own constant of the same name, since no shared module system exists between the two plain scripts to import it for real — so the lens looks fully formed right as the strip visually settles on the first product. This used to be a two-phase split (a fast run to frame 45, then the rest at the clip's native rate, back when that earlier render's motion had settled to an imperceptible wobble by frame 45) — the current render keeps visibly moving well past that point, so the sync mark moved to the very last frame and the split was removed as dead weight; the *reverse* (retreat) still plays at the clip's native rate (`GLASS_NATIVE_FRAME_MS`, 1000/30), unaffected by any of this. `enterGrid()` is idempotent per "past" session via `glassEntered`, since the two inputs above can each call it around the same moment.

**The magnified viewer and label wait for the glass's last frame, not the crossing itself** (`revealMagnifiedContent()`, gated on `glassRevealReady`) — a product's name, and the magnified view, must never be seen floating inside a half-formed glass shape. A product focused while the glass is still short of that frame has its label queued (`labelWaiting`) rather than shown immediately, presented once `revealMagnifiedContent()` actually fires.

**The magnification is real, not a CSS trick.** `--lens-mag` (a `css/style.css` custom property, read once via `getComputedStyle` so the CSS and this file's own layout math can never drift apart) scales a duplicated `<img>` per visible product (`.lens-viewer__mag`, reusing each card's own already-loaded `src` — no extra network requests) plus ONE live 3D viewer, all repositioned every scroll frame by the same lens mapping: a point at viewport offset `d` from the screen's center appears at `MAGNIFICATION * d` from the glass's center. That continuous repositioning is what makes the glass magnify products as they travel through it, not just once one has settled.

**One viewer for the page's whole lifetime**, reused across every product the lens ever shows via `three-viewer.js`'s `loadProduct()`/`returnToDefaultPose()` (see that file's own section above) rather than rebuilt per product — the grid's cards are plain icons now (`js/main.js`), so this is the only WebGL context the page holds. Reworked from an earlier per-product-build design after profiling showed a real cost: rebuilding meant a new context plus a full HDR decode + PMREM regeneration every scroll step, measured at ~180ms of blocked main thread landing as a dropped frame mid-snap.

**The live viewer is drawn where its PRODUCT is, not where the glass is** — positioned by the exact same magnified-stack layout math the still images use, not pinned to the glass's own fixed geometry. That's the piece that lets a model the visitor has set spinning travel *out* of the glass under its own motion (still rendering, still spinning) instead of being swapped for a static replacement the instant it stops being centered.

**A still and the live model are only ever swapped for each other when the two are indistinguishable** — same product, same default pose (the camera stays at the product's own `"3d-viewer-camera-default"`, the exact pose `fallback-img` was captured at, rather than dollying in: a perspective camera's projected size doesn't scale linearly with distance, so a naive "move the camera closer by the magnification factor" would be subtly, visibly wrong — rendering that same pose into a box `--lens-mag`× the disc size has no such error), same size. Two rules follow:
- **Arrival** is instant (a `visibility` toggle, no transition) — there's nothing to ease between, since the live render and the still it replaces are the same picture.
- **Departure** eases the outgoing model back to its default pose first (`viewer.returnToDefaultPose(DEPART_RESET_MS)`), keeping it visible and rendering the whole time, and only hands it back to its still once it actually arrives there. Cutting to the still any earlier would visibly snap a spinning model upright mid-motion — see `three-viewer.js`'s `clearControlsMomentum()` note above for the matching fix on the *next* product's side of the same problem.

**Belt-and-suspenders close** (`syncGlass()`'s own transition-into-the-hero branch, `leaveGrid()`): `js/product-focus.js` has its own, separate boundary for "have we left the strip" — card-geometry-based, with no notion of the hero at all. It normally agrees with the hero-geometry boundary above, but on a phone, where the narrow-screen CSS in `css/style.css` scales the whole lens system by a different factor than the hero's own layout, the two have been observed to disagree by a frame — leaving the label/viewer visibly lingering a beat into the hero. This file's own hero-boundary check forces both closed on its own transition, regardless of what `EmjiveFocus` currently reports, and starts the glass playing frames back down to 1 at the clip's native rate. The actual `glassEntered`/viewer-hiding happens directly in that `syncGlass()` branch rather than inside `leaveGrid()` itself — `leaveGrid()` is also invoked by `EmjiveFocus`'s very first, synchronous "nothing focused yet" ping at subscribe time, before the grid has rendered a single card, and touching that glass-side state there would fire on every page load rather than only a real departure.

Exposes nothing — a leaf consumer of `EmjiveFocus`/`EmjiveModelViewer`/`EmjiveSeries`, not a producer.

## `js/selection.js` (126 lines)

The cart/selection data layer — a thin `localStorage` wrapper. `STORAGE_KEY = "emjive_selection"`. Read/write helpers fall back to `[]` on any error (e.g. corrupted JSON). Every mutating call dispatches `new CustomEvent("emjive:selection-changed")` on `window` — the sole mechanism other scripts use to react live to a change without a page reload.

Four mutators, all index-based (an item's position in the stored array, not an id): `addItem(item)` (pushes to the end), `removeItem(index)` (splices it out), `insertItem(index, item)` (splices it back in at a specific position — `launch-order.html`'s "Undo" after Unselect, so a restored item lands back where it was rather than at the end the way `addItem` would), and `updateItem(index, patch)` (`Object.assign`s `patch` onto the existing item in place — `launch-order.html`'s "Modify," changing metal/size and the price that comes with them without moving the item to the end the way remove+add would).

**Exposes**: `window.EmjiveSelection = { getSelection, addItem, removeItem, insertItem, updateItem, clear, formatPrice, appendSize }`. `appendSize(parent, size)` appends a size value to `parent` as plain text, except a decimal size's fractional part (e.g. `"59.43"`) — that renders in a `.size-fraction` span (`css/style.css`, `font-size: 0.75em`) instead of as a literal `.`, since every place a size is shown after selection (`selection-page.js`'s order rows, `selection-bar.js`'s drawer rows) already joins `.category.metal.size` with literal dots, and a decimal point in the size itself would read as a fourth trait segment.

**Item shape**: `{ series, productId, name, category, metal, size, price, image }` — a deliberately self-contained snapshot, so `launch-order.html` never has to re-fetch or join against any products file to render itself. `series` is what makes `productId` meaningful, since ids are only unique within one series. Selections saved before that field existed simply lack it; nothing here reads it, and `selection-bar.js`'s `itemKey()` tolerates it being absent so an existing cart doesn't read as all-new.

## `js/product.js` (~780 lines) — the largest file

Owns `product.html` end to end. Resolves `?id=` via `findProduct()` — the active series first, then a scan of the remaining series in index order (each memoized), which is what keeps bare `?id=` bookmarks working now that ids are only unique per series. Then renders (by the file's own numbered section comments):

1. **Label** — name, category, per-metal thumbnail, price.
2. **Carousel** — builds slides (a 3D viewer via `window.EmjiveModelViewer` if `product.assets.model` is set, else a fallback icon image, then any `product.assets.photos`). No rim/arrow click zones: navigation is either a free horizontal drag (rubber-band overshoot past either end; release lands exactly where the drag left it, clamped back into bounds — no momentum coast) or a tap directly on a slide, which centers it (`centerOnSlide()`) however far from center it started. On a narrow/phone-width viewport (`isMobileCarousel()` — reuses `css/style.css`'s one existing `max-width: 640px` breakpoint, the `.product-grid` one) a real drag instead always pages exactly one slide forward/backward and centers it, committing only past a real drag distance (15% of a tile) or a fast-enough short flick (gated by a minimum distance too, so touch-event jitter on a barely-moved drag can't read as a flick) — short/slow drags spring back to the slide they started on. A pointer's horizontal-vs-vertical intent is axis-locked in `onPointerMove` (the first movement past a small slop decides it, once) so a vertical scroll starting on the strip is handed off untouched to the browser's own `touch-action: pan-y` instead of the carousel eating part of the gesture; `pointercancel` (the browser interrupting a pointer itself — that same scroll handoff is the common case) is handled separately from a clean `pointerup` specifically so an interrupted gesture is never misread as a tap. Every way a slide gets centered shares one symmetric ease-in-out transition (`CENTER_TRANSITION`; `CANCEL_TRANSITION` is the same curve, shorter, used only when a mobile drag springs back without actually changing slides). Bounds stay "first/last tile centered" (not edge-flush). Carousel geometry can only be measured once `#productDetailContent` is actually visible (`[hidden]` elements measure zero) — bounds are explicitly re-synced right after the content is unhidden.
3. **Metal picker** — re-tints the live 3D model in place via `state.modelHandle.applyMetal(metal)` (no reload, no camera reset), and separately updates the label thumbnail/fallback icon/specs/price, since only the 3D model re-tints itself automatically.
4. **Characteristics** — metal-dependent weight/composition/price from `product["per-metal-specs"][selectedMetal]`.
5. **Select button + size modal** — sizes/units looked up by *category* (not per-product) via `EmjiveSeries.categoryInfo()`. Because that vocabulary is global rather than per-series, a cross-series hit needs no re-hydration. Standard-size buttons + a custom input capped at two decimal places (e.g. `"59.43"`) — a French (or other comma-decimal) mobile keypad's decimal key sends `,`, swapped to `.` before the digit filter runs, or it'd just get stripped. The confirm button (labeled plain "Add") is never actually `disabled` — clicking it with no size chosen instead crossfades its own label into a "First select a size" prompt for 2s (`.size-modal__confirm.is-nudging`, same opacity-crossfade recipe `.order-item__content`/`__overlay` use — see `styling.md`) rather than silently doing nothing. On confirm, calls `window.EmjiveSelection.addItem({...})` with the self-contained snapshot (including the resolved series) and closes the modal.

All page state lives in one `state` object (product, metals, selected metal/size, carousel scroll offset, the live model handle, etc.).

**Notable gotchas** (from the file's own comments): `img.draggable = false` + `dragstart` prevention stops the browser's native image-drag gesture from fighting the custom pointer-drag scroll; a `pointercancel` doesn't reliably carry the pointer's final coordinates, so settling a drag interrupted mid-gesture falls back to the strip's own live position instead of the event's `clientX`; a drag that starts on the 3D model slide is left alone entirely (no `pointerdown` tracking at all) so it rotates the model via `TrackballControls` instead of paging the carousel.

## `js/selection-bar.js` (~340 lines)

The floating bar shown on `index.html` and `product.html` only (not `launch-order.html` — that page isn't in its script list at all, plus it self-guards with `if (!window.EmjiveSelection) return;`). Builds its whole DOM programmatically and appends to `<body>`.

Shows either "No selected item" or a thumbnail strip + "Order ›" link; clicking the bar (not the Order link) opens a drawer with per-item "Unselect" rows. The drawer's `max-height` is set to a real measured pixel value in JS (not a CSS trick) — this is the piece `styling.md`'s drawer note points back to — specifically so it can animate smoothly both on open/close *and* on shrinking while already open (removing a row). `setDrawerOpen(isOpen)` is the one place that changes the drawer's open state — it also registers a panel with `window.EmjiveMenus` so a click away from the bar closes the drawer, same mechanism the header menu uses (see `js/series.js` above).

This file has no notion of **which page it's on**, which was always the point. It does now subscribe to `window.EmjiveHero.onScroll` for the homepage's scroll-driven entrance — but unconditionally: the active series' hero owns all the geometry and publishes how far past its trigger the page has scrolled, and this file measures its own `.selection-bar__summary` height to turn that into a transform. On a page with no hero nothing ever publishes, so nothing ever happens and the bar just stays visible — still zero special-casing. The starting-hidden state is `css/style.css`'s `body.has-series-hero` scoping (see `pages.md` for why that stopped being `:has()`).

Listens for `window.addEventListener("emjive:selection-changed", render)` — this is how it stays live-in-sync with additions from `product.js` or removals from its own drawer.

## `js/selection-page.js` (~690 lines) — `launch-order.html`'s checkout review

Grew enormously from a simple "list + total" renderer into the whole order page's logic: item rows with a Modify/Unselect overlay, per-row undo, a shipping pick, a terms toggle, and the checkout bar's gating — see `pages.md`'s `launch-order.html` section for what all of this actually looks like. `render()` (a full rebuild from `window.EmjiveSelection.getSelection()`) now only runs for the initial page load and after a Modify confirm — Unselect/Undo/the final timeout-collapse each mutate the DOM directly instead, so no row ever moves because of *another* row's undo window.

- **Item row overlay** — `openRowOverlay(li)`/`closeOpenRow()`, one open at a time (opening a new one closes whichever was already open). Mouse hover, a tap, or keyboard focus (`focusin`/`focusout`, chosen over `focus`/`blur` specifically because they bubble, so one delegated listener on the row covers both buttons inside it) all open the same overlay; a click landing elsewhere on an already-open row — anywhere but the Modify/Unselect buttons themselves — closes it back to the normal view instead of being ignored. Both are suppressed on a row that's mid-undo (`binding.pending`) — its overlay has nothing to show. `suppressHoverUntilMove` guards a real browser gotcha: a row's final collapse (`confirmRemoval`, below) reflows whatever's below it up the page, and if the cursor is just sitting still, whichever row's box slides underneath it fires a genuine, unrequested `pointerenter` — this flag makes any such "phantom" enter a no-op until an actual `pointermove` confirms the cursor moved on its own.
- **Per-row undo** (`rowBindings`, one `{ li, item, index, pending, timer, undoBtn }` per row, mirroring `itemsEl`'s children in order) — replaces an earlier shared-stack/shared-bar design. `handleUnselect(binding)` removes the item from storage immediately and crossfades that one row, *in place*, into its own "Undo" prompt (`.order-item__undo-prompt` — same `inset: 0` recipe `.order-item__overlay` uses, so nothing resizes or reflows) rather than collapsing it and showing a bar elsewhere; several rows can be independently mid-undo at once, each with its own `UNDO_TIMEOUT_MS` timer. `shiftIndices(binding, fromIndex, delta)` keeps every *other* binding's `.index` correct whenever one row's item is actually removed from or reinserted into storage, so each row always knows its true current position regardless of how many others are also pending or in what order they resolve — necessary because `EmjiveSelection.getSelection()` re-parses from `localStorage` on every call, so there's no stable object identity to key off instead. `handleUndo(binding)` reinserts at that live index and crossfades straight back — `.order-item__content` was only ever hidden, never rebuilt, so there's nothing to reload. If the window runs out unused, `confirmRemoval(binding)` finally collapses the row for real (`.order-item`'s `is-removing` class, `transitionend` on `max-height` with a 400ms reduced-motion fallback) — or, if `rowBindings` is left empty, skips that and crossfades the *whole list* directly into the empty state instead (`crossfadeToEmpty()`, a hand-orchestrated sequential opacity swap between `#selectionList` and `#selectionEmpty`, needed because `[hidden]` means `display: none`, which can't itself transition).
- **Modify** — `openModifyModal(item, index)` resolves `item.series` (falling back to `EmjiveSeries.slug` for a pre-refactor selection saved without one) and re-fetches that product via `EmjiveSeries.loadProducts()`, since the stored selection snapshot doesn't carry `per-metal-specs`/`icons`. The popup (`#modifyModal`) reuses `product.html`'s own `.size-modal`/`.product-metals` markup and CSS wholesale rather than a page-specific clone — a metal picker plus the standard/custom size picker, pre-filled to the item's current choice, wired almost identically to `product.js`'s `wireSelectButton()` — including the same custom-input two-decimal cap and comma-to-dot swap — except the static controls (input/guide toggle/backdrop/confirm/Escape) are wired exactly once and read a mutable `modifyState` object rather than closing over one fixed product, since a different row's item can sit behind this same modal on each open. Unlike "Add," "Save" (`modifyModalConfirm`) still just toggles `.disabled` directly and has no nudge — a pre-filled item always has *some* size going in, so it's never expected to actually need one. Confirms via `window.EmjiveSelection.updateItem()`, recomputing price from the newly-selected metal's `per-metal-specs`, then a full `render()` — which silently ends any *other* row's still-pending undo early, since that rebuild repopulates straight from current storage with no way to carry mid-flight per-row state across it. Rare enough (needs two different rows mid-interaction at once) not to be worth engineering around.
- **Shipping/terms/checkout** — `SHIPPING_OPTIONS`, a small in-file placeholder array (easy to extend later, not a restructure), rendered as a single-select dot-indicator list. The terms row's click is delegated across the whole element (the dedicated tick-box or the surrounding sentence both toggle; a click on the actual `<a>` to `terms.html` navigates instead — same "toggle vs. its own separately-clickable label" split `selection-bar.js`'s drawer toggle/empty-label pair uses). `updateCheckoutGate()` disables `#orderCheckoutButton` until both a shipping option is selected and terms are ticked. The button itself is a stub — no Stripe session exists yet, so a click (once enabled) just `alert()`s that it isn't connected, the same convention `main.js`'s guarded `#contactForm` handler uses.

## Cross-cutting contracts (the highest-value section if you're changing behavior that spans files)

- **`window.EmjiveSeries`** — set by `js/series.js` (blocking, in `<head>`), consumed by `main.js`, `product.js` and `series-page.js`. The one place "which series is this, and where's its data" lives.
- **`window.EmjiveHero`** — set by `js/series.js`, published to by the active series' `hero.js`, subscribed to by `selection-bar.js`. A plain function registry, one number: how far past the hero's trigger point the page has scrolled.
- **`window.EmjiveMenus`** — set by `js/series.js`, registered with by `main.js` (header menu), `selection-bar.js` (drawer), and `selection-page.js` (each item row's Modify/Unselect overlay, one at a time). Click-away coordination: a click outside every currently-open panel's root closes only the most-recently-opened one.
- **`window.EmjiveSeriesHero`** — set by a series' `hero.js`, called by `js/series.js`. `{ init(root, ctx), onProducts(products) }`.
- **`window.EmjiveModelViewer`** — set by `three-viewer.js`, consumed by `js/lens-artefact.js` (the homepage's one reused viewer), `product.js` (carousel), and `scene-tool.html` (a standalone dev tool, `options.freeOrbit`/`options.primitive`). The one place 3D viewer construction/materials/camera behavior lives. **Not** `main.js` any more — see that file's own section above.
- **`window.EmjiveGrid`** — set by `main.js` on every `applyFilter()` call (the initial render included), read once at init by `product-focus.js`/`lens-artefact.js` alongside their own `"emjive:grid-changed"` listeners. Exists purely to cover a warm-cache race the event alone can't: `{ entries: cards }`, the same array the event's `detail.entries` carries.
- **`"emjive:grid-changed"`** — `CustomEvent` on `window`, dispatched by `main.js` alongside every `window.EmjiveGrid` update. `product-focus.js` and `lens-artefact.js` both listen — the one funnel either has for "which cards are visible right now."
- **`window.EmjiveFocus`** — set by `product-focus.js`, consumed by `lens-artefact.js` (`onChange`/`onSettled`/`entries`) and `main.js` (`goHome`, the brand logo's click handler). `{ onChange(fn), onSettled(fn), entries(), goHome() }` — which product is centered in the grid's snap-scroll strip, whether the strip has stopped moving, and a way to cancel any in-flight snap and return to the top of the page.
- **`window.EmjiveSelection`** — set by `selection.js`, consumed by `product.js` (add), `selection-bar.js` (add/remove/read, plus `appendSize` for its own row display), `selection-page.js` (remove/insert/update/read, plus `appendSize`).
- **`"emjive:selection-changed"`** — `CustomEvent` on `window`, dispatched by every `selection.js` mutation. Only `selection-bar.js` listens for it.
- **`localStorage["emjive_selection"]`** — the persisted selection array (via `selection.js`).
- **`sessionStorage["emjive_model_interacted"]`** — unrelated to selection; remembers within a browsing session whether the visitor has already discovered models are draggable, to stop nudging them with the wiggle hint (set/read in `three-viewer.js`).
- **`sessionStorage["emjive_grid_position"]`** — the homepage grid's own scroll-position breadcrumb (`product-focus.js`), saved on `pagehide` and consumed on the next load of `index.html` (typically a back-navigation) to restore instantly to the same product.
- **Item shape**: `{ series, productId, name, category, metal, size, price, image }` (see `selection.js` above).

## `js/series-page.js` (~55 lines)

`series.html` only. Resolves the slug via `EmjiveSeries.requestedSlug()` — deliberately **not** the fallback-applying `.slug` — loads that series' manifest, fills in the title/year/subtitle, and otherwise shows a not-found state. Rendering `manifest.json`'s `sections[]` belongs here later; the page is an empty shell by design.
